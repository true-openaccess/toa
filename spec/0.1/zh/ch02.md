## 2 对象名

### 2.1 写法

```text
对象名 = 前缀 "_" 哈希
前缀   = 一个小写字母，后跟 1 到 7 个小写字母或数字     共 2 到 8 个字符
哈希   = 40 个字符，每个是 0-9 或 a-f                   小写十六进制
```

- **切分规则。** 对象名里有且只有一个下划线。下划线之前是前缀，之后是哈希。前缀和哈希里都没有下划线。
- **哈希部分固定 40 位。** 它是按 2.2 节算出的值，写全，不截短，不用大写。
- **比较对象名时整串比较，** 区分大小写。判断一个字符串是不是对象名时必须整串匹配，前后不得有多余字符，换行也算。
- **保留的形式。** `prefix_` 后跟 64 位小写十六进制，留给以后换哈希算法时用。
  - `0.1` 的库里不得出现这种名字。它本来也超过了名字 64 个字符的上限（3.1）。
  - 工具在工作目录里遇到这种名字的目录，不得进入、改名或删除，应当报告。
  - 别的长度没有特殊含义：`tb_ac` 就是一个普通的字符串。
- **前缀就是类型的名字。** 入口文件里的 `type` 必须和前缀一字不差（3.2）。类型只有这一套名字。对象的身份由哈希决定。
- **一份内容只有一个前缀合格。** 入口文件在哈希里，`type` 又必须等于前缀，所以同一份内容换一个前缀就不是合格的对象。任何工具都查得了这一条，不需要认识这个类型。不另外检查"一份内容一个名字"。
  - 同一个对象在一个库里放几份不算错（6.2）。
- **工具遇到不认识的前缀，** 必须照样把这个目录当对象：能列出、核对名字和 `type`、拷贝、按名字取、带着旁挂文件走。可以不检查类型规格，不展示细节。

### 2.2 哈希怎么算

先定义一组文件的哈希。输入是若干路径，每条路径对应一个文件的字节；路径用 `/` 分成各级目录。

1. **文件的哈希：** `SHA-1("blob " + 文件字节数的十进制写法 + 一个 0 字节 + 文件的全部字节)`。
2. **目录的哈希：** 列出这个目录的直接成员，每个成员一条：
   - 文件：`"100644 " + 文件名 + 一个 0 字节 + 该文件的哈希（20 个原始字节）`；
   - 子目录：`"40000 " + 目录名 + 一个 0 字节 + 该子目录的哈希（20 个原始字节）`。
   - 各条按名字的字节序排序，子目录的名字排序时当作结尾多一个 `/`。
   - 把各条首尾相接得到正文。目录的哈希是 `SHA-1("tree " + 正文字节数的十进制写法 + 一个 0 字节 + 正文)`。
3. **这组文件的哈希**是最上面那个目录的哈希，写成 40 位小写十六进制。

- **对象的哈希**是对象目录里全部文件按上面算出的值。**只有合法的对象树（3.1）才有对象的哈希：** 不合规的目录必须报不合格，不得跳过不合规的成员后照算。
- **文件按字节原样算：** 不做换行转换，不做任何过滤。
- **哈希只取决于目录里的文件名和文件内容，** 和目录叫什么、放在哪、在哪个提交里无关。
- **不经 git 算哈希时，** 应当用带碰撞检测的 SHA-1 实现；检测到碰撞的对象必须判为不合格。
- **和 git 的关系。** 在守 3.1 节和 6.1 节规则的库里，这个值等于 git 给该目录存的 tree 号。这是由规则推出的，不是定义。有两种情况两者不同，都以本节的算法为准：
  - 仓库的设置不合规（换行转换、过滤器、忽略规则），git 存进去的不是工作目录里的字节。
  - git 仓库里存的目录树不是规范写法：模式前面多写了 0、成员没按顺序、成员名里带 `/`。git 给这样的树另一个号。按目录列表核对时必须把它查出来（7.4）。
- **对照值：** 同样的三步，把 SHA-1 换成 SHA-256（文件和子目录的哈希是 32 个原始字节），得到一个 64 位十六进制的值。它不是名字的一部分，只用来做第 11 章说的独立核对。它等于 git 的 SHA-256 对象格式给同一个目录算的 tree 号。

### 2.3 测试向量

| 目录内容（文件名：内容） | 哈希 | 对照值（SHA-256） |
|---|---|---|
| `toa.yaml`：`type: doc\nlicense: MIT\n`；`README.md`：`hello\n` | `ea44863a8d2f242bc651caf709d45a27e7531d9d` | `e282624f05b86cc1bae3ef0abf32ad2540fb72fc15d309cea0988289b9ee2bd9` |
| `a.txt`：`1\n`；`a/z`：`2\n`；`a-b`：`3\n`；`a0`：`4\n`（考排序：`a-b`、`a.txt`、目录 `a`、`a0`） | `497bcf8f72cdfb77f6ab7d4e0ac6cfeaafa81c8c` | `6405c1e3597fbe6fd1f4f30a3f99bed0edb1858cb9d72e829ee1116ce4012b7d` |
| `empty`：空文件；`crlf.txt`：`x\r\n`（考字节原样） | `372f060b024c23ddf17d022472fff124c6d37efb` | `cd440b4b25949dc63433404279def2ffcb0ff07a3a3ad3c3b0177b1078df2d4c` |

- `\n` 是一个换行字节（0x0A），`\r` 是 0x0D。三行的两个值都用 git 核对过，SHA-1 格式和 SHA-256 格式的仓库各一次。
- 后两行只用来考算法：它们没有 `toa.yaml`，不是合格的对象，有的只是"一组文件的哈希"。
- **不规范写法的树。** 第一行的两个文件，如果 git 的目录树把 `toa.yaml` 的模式写成 `0100644`，号是 `88877fcc08dc665dc776a5f121bebfd1bc99469e`；两条的顺序写反，号是 `ac31b57cf9c3bd3ff8bd22112d2b5e480e6ffad1`。这两个都不是这组文件的哈希，名字取它们的目录不是合格的对象。
- 这些向量、这两棵树，以及对象名和草稿名的更多向量，在 `vectors/` 里（1.6）。

### 2.4 草稿名

- **还没定稿的对象目录用草稿名：** `<prefix>_draft-<tag>`，即"前缀_draft-标签"。标签是 1 到 40 个小写字母、数字或连字符，以字母或数字开头。
- **草稿名不可能是对象名，** 因为它的下划线之后不是 40 位十六进制。
- **标签里没有点。** 草稿的旁挂文件叫 `<draft name>.notes/` 和 `<draft name>.source.jsonl`，它们带点，所以不会被当成另一个草稿。
- **这个形式是保留的：** 入口文件、`lock.json` 和 `members.source.jsonl` 里任何整串符合草稿名形式的值，都被当作对一个草稿的引用。任何类型规格都不得允许字段取这种形式的值。
- **草稿名不得出现在发布分支上。** 这包括：
  - 目录名和文件名，以及以"草稿名加点"开头的名字；
  - 每个对象的 `toa.yaml` 里任何位置的值；
  - 每个对象的 `lock.json` 里的值；
  - 每个对象的 `members.source.jsonl` 里的值。
- 别的分支上可以有草稿。
