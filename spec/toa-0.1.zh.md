# TOA 库格式标准 0.1 版（中文版）

TOA（true open access）是一套设计库的格式标准。对象和引用都是普通的文件：对象名和 git 的 tree 哈希算出来相同，但算的时候不需要 git。`0.1` 版用 git 仓库发布和共享对象，所以同一个库线上线下、公开私有都能用。每个对象按它内容的哈希命名，所以一个名字永远指同一份内容。本文是 `0.1` 版的标准。

- 英文版是正式文本。本文是它的中文译本，即 `toa-0.1.zh.md`；两者不一致时，以英文版为准。只有英文术语是规范的术语；每种译本各有自己的术语表。
- `types/` 里的类型规格是本标准的一部分：每份规定一种对象（第 9 章）。
- `vectors/` 里的测试向量是说明性的。它和正文不一致时，以正文为准（1.6）。
- `0.x` 各版本之间不承诺兼容（第 10 章）。
- 任何工具、网站、EDA 集成都可以照本标准实现。配套的参考工具 `toa` 和本标准一起发布。

## 1 概述

### 1.1 范围

TOA 是设计库的一种格式：一个模块定义、它的各个电路网表、电路网表的测试用例和验证记录、关于它们的文档，以及把其中一组冻结下来的冻结库，都按它存放。其中每一样是一个对象，也就是一个按内容的哈希命名的目录。对象本身不依赖 git：对象名里的哈希就是 git 算出的 tree 哈希，但算它不需要 git（2.2）。`0.1` 版通过库发布和共享对象，库是 git 仓库；在一台机器上，对象也可以放在普通目录里，由来源表的 `local` 来源指过去（5.1）。对象之间按名字引用，所以一个设计不管它的对象放在哪里，都是同一个设计。

本标准规定：

- 对象怎样命名，名字怎样从文件算出（第 2 章）；
- 对象目录里可以有什么，它的入口文件、引用和来历（第 3 章）；
- 对象旁边的文件：说明、来源表和删除记录（第 4 章）；
- 来源表：说明到哪里能找到对象（第 5 章）；
- 库：库是什么，对象在库里怎样摆，库必须过哪些检查（第 6 章）；
- 对对象的操作：定稿、发布、取对象、核对、跟进更新、组装（第 7 章）；
- 工作区清单和索引（第 8 章）；
- 对象的类型怎样登记、怎样规定（第 9 章），标准怎样演进（第 10 章）；
- 安全上必须写明的事（第 11 章）。

TOA 不规定：哪个库收哪些许可证，谁能往库里写，投稿怎么审，账号从哪来，网站长什么样。这些由每个部署自己定。

### 1.2 本标准的结构

第 2 到 4 章规定对象，第 5、6 章规定对象放在哪，第 7、8 章规定工具拿对象做什么。第 9 章登记对象的类型；每种类型另有自己的类型规格，在 `types/` 里。附录 A 列出正文各处定的上限，附录 B 列出留给以后版本的内容。两个附录都是说明性的，注和例子也是。其余都是规范性的。

### 1.3 要求用词

- **必须**、**不得**：硬性要求。对象或库不满足，就不是合格的 TOA 对象或 TOA 库；工具不满足，就不符合本标准（1.6）。
- **应当**、**不应当**：建议。可以有理由不照做，但先要弄清楚那些理由。
- **可以**：允许。

### 1.4 术语

| 术语 | 含义 |
|---|---|
| 祖先（ancestor） | 另一个对象的来历名单里点到的对象（3.4） |
| 摆法（arrangement） | 一个库里的对象怎样分目录放。只有对象目录的名字有意义（6.2） |
| 组装（assemble） | 把一个电路网表连同它的展开树变成一组可以直接仿真的文件（7.6） |
| 检查（check） | 看是否守本标准的规则，例如库的检查（6.4）。不要和"核对"混淆 |
| 对照值（cross-check hash） | 用 SHA-256 代替 SHA-1、按对象哈希的算法算出的值。不是名字的一部分，只用来做独立的核对（2.2） |
| 部署（deployment） | 使用 TOA 的一方，例如一个库、一个平台、一个 CI 服务；本标准没有规定的事由它定 |
| 草稿（draft） | 还没定稿的对象目录。它的名字是草稿名（2.4） |
| 展开树（expanded tree） | 一个电路网表，加上它经 `uses` 采用的电路网表，一层层到底（7.6） |
| 外部文件（external file） | 对象需要、但不随它发布的文件，例如 PDK 的模型文件（3.5） |
| 取对象（fetch） | 按名字拿到一个对象的文件（7.3） |
| 冻结库（frozen library） | 把一组对象冻结下来的对象，例如一个库的一次发布：一份来源表格式的成员表（类型 `lib`）。不要和"库"混淆 |
| 代（generation） | 给人看的：一个对象在它那一支里是第几代：第一个是 1，往后每个比它的上一代多 1。定稿把它写进 `history.json`（3.4） |
| 分组（group） | 来源表给对象标的 1 到 4 段的路径，例如库、设计。只给人看（5.1） |
| 来历名单（history） | 一个对象沿 `base` 第一项往上的祖先名单，和它的代数一起在它的 `history.json` 里（3.4） |
| 索引（index） | 读库得到的派生数据：谁引用了一个对象，它在哪、什么时候出现，各库对它说了什么（8.2） |
| 库（library） | 一个放对象的 git 仓库，指整个仓库：`0.1` 版就用它发布和共享对象。只回答"对象放在哪"（6.1）。放在本机普通目录里的对象不在任何库里 |
| 库的检查（library check） | 库的维护者在移动发布分支之前，对每个新提交做的检查（6.4） |
| 库的清单（library list） | 库顶层的来源表 `library.source.jsonl`，列出库里的全部对象（5.2） |
| 最新标记（latest mark） | 库的清单里对象行上的 `"latest": true`：这个库推荐用这个对象，取代它那一支里之前的各代（5.1、7.5） |
| 来历（lineage） | 一个对象是从哪些对象改来的：`base` 和 `history.json`（3.4）。不要和"来源"混淆 |
| 本机映射表（local file map） | 使用者本机的一份文件，说明每个工艺和每个外部文件在本机对应哪个文件；不进任何公开的库（3.5、7.6） |
| 入口文件（manifest） | 每个对象顶层的 `toa.yaml`：写它的类型、许可证、引用和类型规格要的字段（3.2） |
| 说明（note） | 对象的说明目录里的一份文件：一个库对它的补充，发布之后不再改（4.1） |
| 对象（object） | 名字由内容算出的一个目录，顶层有一份入口文件。不可变（第 3 章） |
| 对象名（object name） | `<prefix>_<hash>`，即"前缀_哈希"，对象的名字（2.1） |
| 前缀（prefix） | 对象名里下划线之前的部分，也是对象类型的名字（2.1） |
| 发布分支（publication branch） | 库里别人该看的那个分支。是哪一个由用库的人说，默认 `main`（6.3） |
| 已发布（published） | 在一个库发布分支最新的提交里（6.3） |
| 可读名（readable name） | 推荐摆法里对象目录之前、给人看的那几级目录名，例如 `strongarm-comp/wrap-lee.g2`（6.2） |
| 引用（reference） | 入口文件或 `lock.json` 里整串是对象名的值，或者 `members.source.jsonl` 里一行的对象（3.3） |
| 删除记录（removal record） | 对象删掉之后可以留在原处的一份文件：删的是什么，从哪来，到哪还能找到（4.2） |
| 一支（series） | 一个设计的各代：类型相同、`name` 相同，沿 `base` 第一项连起来的对象（3.4） |
| 定稿（seal）、取消定稿（unseal） | 定稿把草稿变成对象：算出名字，改目录名，用名字换掉草稿名。取消定稿把还没发布的对象变回草稿（7.1） |
| 旁挂文件（sidecar file） | 对象目录旁边、名字以对象名开头的文件或目录：说明目录、来源表、删除记录和时间戳目录。不属于对象（第 4 章） |
| 来源（source） | 到哪里能取到一个对象：一个 git 仓库或一个本机目录（5.1）。不要和"来历"混淆 |
| 来源表（source list） | 按第 5 章格式写的对象清单，每个对象带缓存的信息和已知的来源；可以包含别的来源表。库的清单和工作区清单都是来源表 |
| 类型（type）、类型规格（type specification） | 对象的种类，由前缀命名；写明一种对象有哪些字段和文件的文档（第 9 章） |
| 合格（valid） | 满足本标准适用的每一条要求；反过来是不合格 |
| 核对（verify） | 重算对象的哈希，和名字比较（7.4）。不要和"检查"混淆 |
| 合法的对象树（well-formed object tree） | 守 3.1 规则的目录；这些规则只看名字、成员的种类和大小 |
| 工作区清单（workspace list） | 使用者工作目录里的一份来源表，列出当前设计用到的全部对象，通常是包含几个库的清单（8.1） |

### 1.5 原则

- **对象只靠名字认出。** 名字相同就是同一个对象，不管它在哪个库、哪个镜像、哪个拷贝里。
- **引用只写名字，不写地址。** 对象在哪，由来源表（包括工作区清单）和索引回答，它们都在对象之外。
- **对象不可变。** 内容的任何改动都得到另一个名字，也就是另一个对象（3.6）。

从这几条原则可以得出 TOA 的两个特点。这里写出来是为了读者，不增加任何要求：

- **设计自己能拼起来。** 只要每个对象旁边都带着它的来源表（第 4 章），这份表就说明了它和它引用的对象在哪里找得到（5.2）。从一个对象出发，顺着引用走，工具就能收齐这个对象需要的一切：例如从一条验证记录出发，收齐被测的电路网表、它用到的整棵电路网表树、各个测试用例和模块定义。不需要任何人维护的目录或登记处（7.3、7.6）。
- **改动藏不住。** 对象由名字固定，名字是内容的哈希，它引用的对象的名字又是内容的一部分。改动任何一个对象都会得到另一个名字：原来引用它的对象仍然引用原来那个，自己不变，也不会悄悄变成指别的东西。拿到对象的人都可以重算名字，看它是不是名字所指的那一份（7.4）。`base` 和 `history.json`（3.4）记下每个对象从哪里改来，所以一个设计的各代可以按名字一个个往回查。

### 1.6 一致性

本节把其他各章的要求按它们管的对象汇总在一起，不另加要求。

- **合格的对象**有一个对象名（2.1），是一棵合法的对象树（3.1），它的哈希就是名字里的哈希（2.2）。它的入口文件守 3.2，`type` 就是它的前缀；有 `history.json`、`lock.json`、`members.source.jsonl` 的，分别守 3.4、3.3、3.3。认识这种类型的工具再按它的类型规格检查（第 9 章）；不认识的做不了这一步，在它能查的范围内这个对象仍然合格。
- **合格的库**守 6.1，发布分支上的每个提交都过得了库的检查（6.4）。
- **符合本标准的工具**守它所做的事的要求：
  - 读对象的工具都要把不认识的前缀当对象（2.1），忽略不认识的字段（3.2），按容错的读法读别人的来源表（5.1）；
  - 定稿的工具守 7.1，发布的工具守 7.2；
  - 取对象的工具守 7.3 的步骤；
  - 核对的工具守 7.4，并在 7.4 列的场合核对；
  - 删除对象的工具守 6.5，写删除记录的工具守 4.2；
  - 建索引的工具守 8.3，组装的工具守 7.6；
  - 所有工具都守第 11 章。
- **测试向量。** `vectors/` 里的测试向量对每个输入给出它合不合格，以及它守或违反的是哪一节。工具对一个向量判出的合格与否和向量相同，就算通过；不要求报出节号。测试向量是说明性的：它和正文不一致时，以正文为准。

## 2 对象名

### 2.1 写法

```text
对象名 = 前缀 "_" 哈希
前缀   = 一个小写字母，后跟 1 到 7 个小写字母或数字     共 2 到 8 个字符
哈希   = 40 个字符，每个是 0-9 或 a-f                   小写十六进制
```

- **切分规则。** 对象名里有且只有一个下划线。下划线之前是前缀，之后是哈希。前缀和哈希里都没有下划线。
- **哈希部分固定 40 位。** 它是按 2.2 节算出的值，写全，不截短，不用大写。
- **比较对象名时整串比较，** 区分大小写。判断一个字符串是不是对象名时必须整串匹配，前后不得有多余字符，换行也算。
- **保留的形式。** `prefix_` 后跟 64 位小写十六进制，留给以后换哈希算法时用。
  - `0.1` 的库里不得出现这种名字。它本来也超过了名字 64 个字符的上限（3.1）。
  - 工具在工作目录里遇到这种名字的目录，不得进入、改名或删除，应当报告。
  - 别的长度没有特殊含义：`tb_ac` 就是一个普通的字符串。
- **前缀就是类型的名字。** 入口文件里的 `type` 必须和前缀一字不差（3.2）。类型只有这一套名字。对象的身份由哈希决定。
- **一份内容只有一个前缀合格。** 入口文件在哈希里，`type` 又必须等于前缀，所以同一份内容换一个前缀就不是合格的对象。任何工具都查得了这一条，不需要认识这个类型。不另外检查"一份内容一个名字"。
  - 同一个对象在一个库里放几份不算错（6.2）。
- **工具遇到不认识的前缀，** 必须照样把这个目录当对象：能列出、核对名字和 `type`、拷贝、按名字取、带着旁挂文件走。可以不检查类型规格，不展示细节。

### 2.2 哈希怎么算

先定义一组文件的哈希。输入是若干路径，每条路径对应一个文件的字节；路径用 `/` 分成各级目录。

1. **文件的哈希：** `SHA-1("blob " + 文件字节数的十进制写法 + 一个 0 字节 + 文件的全部字节)`。
2. **目录的哈希：** 列出这个目录的直接成员，每个成员一条：
   - 文件：`"100644 " + 文件名 + 一个 0 字节 + 该文件的哈希（20 个原始字节）`；
   - 子目录：`"40000 " + 目录名 + 一个 0 字节 + 该子目录的哈希（20 个原始字节）`。
   - 各条按名字的字节序排序，子目录的名字排序时当作结尾多一个 `/`。
   - 把各条首尾相接得到正文。目录的哈希是 `SHA-1("tree " + 正文字节数的十进制写法 + 一个 0 字节 + 正文)`。
3. **这组文件的哈希**是最上面那个目录的哈希，写成 40 位小写十六进制。

- **对象的哈希**是对象目录里全部文件按上面算出的值。**只有合法的对象树（3.1）才有对象的哈希：** 不合规的目录必须报不合格，不得跳过不合规的成员后照算。
- **文件按字节原样算：** 不做换行转换，不做任何过滤。
- **哈希只取决于目录里的文件名和文件内容，** 和目录叫什么、放在哪、在哪个提交里无关。
- **不经 git 算哈希时，** 应当用带碰撞检测的 SHA-1 实现；检测到碰撞的对象必须判为不合格。
- **和 git 的关系。** 在守 3.1 节和 6.1 节规则的库里，这个值等于 git 给该目录存的 tree 号。这是由规则推出的，不是定义。有两种情况两者不同，都以本节的算法为准：
  - 仓库的设置不合规（换行转换、过滤器、忽略规则），git 存进去的不是工作目录里的字节。
  - git 仓库里存的目录树不是规范写法：模式前面多写了 0、成员没按顺序、成员名里带 `/`。git 给这样的树另一个号。按目录列表核对时必须把它查出来（7.4）。
- **对照值：** 同样的三步，把 SHA-1 换成 SHA-256（文件和子目录的哈希是 32 个原始字节），得到一个 64 位十六进制的值。它不是名字的一部分，只用来做第 11 章说的独立核对。它等于 git 的 SHA-256 对象格式给同一个目录算的 tree 号。

### 2.3 测试向量

| 目录内容（文件名：内容） | 哈希 | 对照值（SHA-256） |
|---|---|---|
| `toa.yaml`：`type: doc\nlicense: MIT\n`；`README.md`：`hello\n` | `ea44863a8d2f242bc651caf709d45a27e7531d9d` | `e282624f05b86cc1bae3ef0abf32ad2540fb72fc15d309cea0988289b9ee2bd9` |
| `a.txt`：`1\n`；`a/z`：`2\n`；`a-b`：`3\n`；`a0`：`4\n`（考排序：`a-b`、`a.txt`、目录 `a`、`a0`） | `497bcf8f72cdfb77f6ab7d4e0ac6cfeaafa81c8c` | `6405c1e3597fbe6fd1f4f30a3f99bed0edb1858cb9d72e829ee1116ce4012b7d` |
| `empty`：空文件；`crlf.txt`：`x\r\n`（考字节原样） | `372f060b024c23ddf17d022472fff124c6d37efb` | `cd440b4b25949dc63433404279def2ffcb0ff07a3a3ad3c3b0177b1078df2d4c` |

- `\n` 是一个换行字节（0x0A），`\r` 是 0x0D。三行的两个值都用 git 核对过，SHA-1 格式和 SHA-256 格式的仓库各一次。
- 后两行只用来考算法：它们没有 `toa.yaml`，不是合格的对象，有的只是"一组文件的哈希"。
- **不规范写法的树。** 第一行的两个文件，如果 git 的目录树把 `toa.yaml` 的模式写成 `0100644`，号是 `88877fcc08dc665dc776a5f121bebfd1bc99469e`；两条的顺序写反，号是 `ac31b57cf9c3bd3ff8bd22112d2b5e480e6ffad1`。这两个都不是这组文件的哈希，名字取它们的目录不是合格的对象。
- 这些向量、这两棵树，以及对象名和草稿名的更多向量，在 `vectors/` 里（1.6）。

### 2.4 草稿名

- **还没定稿的对象目录用草稿名：** `<prefix>_draft-<tag>`，即"前缀_draft-标签"。标签是 1 到 40 个小写字母、数字或连字符，以字母或数字开头。
- **草稿名不可能是对象名，** 因为它的下划线之后不是 40 位十六进制。
- **标签里没有点。** 草稿的旁挂文件叫 `<draft name>.notes/` 和 `<draft name>.source.jsonl`，它们带点，所以不会被当成另一个草稿。
- **这个形式是保留的：** 入口文件、`lock.json` 和 `members.source.jsonl` 里任何整串符合草稿名形式的值，都被当作对一个草稿的引用。任何类型规格都不得允许字段取这种形式的值。
- **草稿名不得出现在发布分支上。** 这包括：
  - 目录名和文件名，以及以"草稿名加点"开头的名字；
  - 每个对象的 `toa.yaml` 里任何位置的值；
  - 每个对象的 `lock.json` 里的值；
  - 每个对象的 `members.source.jsonl` 里的值。
- 别的分支上可以有草稿。

## 3 对象目录

### 3.1 合法的对象树

一个目录是合格的对象，必须同时满足：

1. **只有普通文件和目录：** 没有符号链接、目录联接、子模块、设备文件，没有空目录。在 git 里，成员的模式只能是 `100644` 和 `40000`，所以文件不带可执行位。
2. **顶层有一份 `toa.yaml`，是普通文件**（3.2）。顶层的 `history.json`（3.4）、`lock.json` 和 `members.source.jsonl`（3.3）不管什么类型都有固定含义，出现时必须是普通文件。
3. **每一级的名字**（文件名，和路径上每一级目录的名字）：
   - 只用 `A-Z a-z 0-9 . _ -`，长度 1 到 64；
   - 第一个字符是字母、数字或下划线。所以没有以点开头的名字：`.git`、`.gitattributes`、`.gitignore`、`.gitmodules` 都不会出现在对象里；
   - 不以点结尾；
   - 第一个点之前的部分，不分大小写，不是 `con`、`prn`、`aux`、`nul`、`com0` 到 `com9`、`lpt0` 到 `lpt9`。
4. **同一个目录下，没有两个名字只差大小写。**
5. **对象里任何一级的名字都不是对象名或草稿名。** 对象互不嵌套。
6. **上限：**
   - 对象目录之下最多再套 6 层目录：文件的相对路径里最多 6 个 `/`；
   - 对象内任何文件的相对路径不超过 80 个字符；
   - 文件总数不超过 2,000；
   - 单个文件不超过 10 MiB，整个对象不超过 50 MiB。库可以定得更严。

- **这些规则只看名字、成员的种类和大小，** 不读文件内容。
- **在 git 的目录列表上查时，** 还要查两件事：同一条路径不重复出现；每条路径经过的每一级目录，都作为目录列在列表里。git 的目录树里可以有一个名字带 `/` 的成员，它在列表里看起来像一条普通的路径，查这一条才认得出来。
- **在没有权限位的文件系统上（Windows），** 读文件核对时不查可执行位。定稿时的第二遍计算（7.1）和库的检查会查出来。
- 取用别处的对象时，必须在写盘之前按它的目录列表查一遍（7.3）。

### 3.2 入口文件 `toa.yaml`

#### 3.2.1 公共字段

- **每个对象顶层有且只有一份入口文件 `toa.yaml`。** 所有类型都叫这个名字。
- **公共字段：**

  | 字段 | 要求 | 含义 |
  |---|---|---|
  | `type` | 必须 | 对象的类型：就是它的前缀，一字不差，例如 `ckt`。前缀碰巧是 `on`、`no` 这类词时加引号（3.2.3 第 10 条） |
  | `license` | 必须 | 整个对象的许可证，写成 SPDX 许可证表达式（3.2.2） |
  | `author` | 可以 | 自由文字的署名。随内容固定，不是身份凭据（见下） |
  | `base` | 可以 | 一个或多个对象名的列表：这个对象直接从哪些同类型的对象改来（3.4）。没有就不写这个字段 |
  | `title` | 可以 | 一行标题，不超过 200 个字符。模块定义必须写 |
  | `description` | 可以 | 用一段或几段话说这个对象是什么。更长的写进 `README.md` |
  | `tags` | 可以 | 用来查找它的词的列表 |

- **其余字段由类型规格定**（第 9 章）。
- **`author` 跟着内容走。** 它在入口文件里，因而在哈希里：原样传播的每一份副本都保留它，换了 `author` 的副本是另一个对象、另一个名字。它不是身份凭据：谁都能写任何名字。是谁把对象放进一个库，由签名的提交说明（6.3）；对象某天以前已经存在，由第 11 章的证据说明。
- **字段名。** 本标准和各类型规格定义的每个字段，名字都是一个小写英文词。要两个词的，改成嵌套，例如 `simulator: {name, version}`。不禁止下划线，只是标准字段都不用。这里只管字段名：值，例如端口名、子电路名、指标名和测试用例名，照各自的规则。
- **入口文件里没有对象自己的名字。** 文件不能包含自己的哈希。

#### 3.2.2 许可证

- `license` 必须合 SPDX 许可证表达式的语法：许可证标识、`LicenseRef-<name>`、`AND`、`OR`、`WITH`、括号和 `+`。
- 不得用 `DocumentRef-…`：它指向对象之外的一份 SPDX 文档。`NONE`、`NOASSERTION` 不是许可证表达式，也不得用。
- 表达式里的每个 `LicenseRef-<name>`，对象里都必须有一个文件名以 `LICENSE` 开头、内容是这个许可证全文的文件。
- 许可证标识应当在 SPDX 许可证表里。工具认不出某个标识时应当给警告，不得因此判对象不合格：表会增加，工具不必跟着更新。
- 对象里的文件带不带许可证文件头、文件头怎样和 `license` 一致，由类型规格定。

#### 3.2.3 写法

入口文件是 YAML 的一个子集。下面的规则只看文件怎么写，不依赖任何 YAML 库对 `1.1` 版或 `1.2` 版 YAML 的理解。照这些规则，工具不用 YAML 库也能读入口文件。

1. **整个文件：** UTF-8，不带 BOM。换行只有 LF，文件以 LF 结尾。不含 CR、NUL、U+0085、U+2028、U+2029（字符串里要这些字符时，用双引号加转义）。不超过 256 KiB。
2. **一个文档：** 不用指令（`%YAML`、`%TAG`），没有 `---` 或 `...` 这样的行。顶层是块式映射，键从第一列开始。嵌套不超过 16 层，顶层映射算第 1 层。
3. **不用锚点、别名、标签。** 同一个映射里没有重复的键。键都是字符串。不用复杂键（`?`）。
4. **缩进只用空格。** 除了带引号的标量里面和块标量的正文，任何地方都没有制表符。
5. **各占一行：** 不带引号的标量、带引号的标量、流式集合，都在同一行里开始和结束。多行的文字写成块标量。
6. **块式集合：**
   - 映射的一项是键、`:`，之后要么是一个空格和同一行上的值，要么什么都没有。什么都没有时，值是下面几行的块式集合：它比键缩进得多，序列也可以和键缩进得一样多；下面没有这样的行时值为空。
   - 序列的一项是 `-`，之后要么是一个空格和一个值；要么是一个空格和一个映射的第一项，这个映射的其余各项和第一个键对齐到同一列；要么什么都没有，值是下面几行比 `-` 缩进得多的块式集合。
   - 同一个集合的各项缩进相同。
7. **块标量：** 头是 `|`、`|-`、`>` 或 `>-`，此外没有别的；头所在的行上，头之后什么都没有。正文在下面几行，比头所在的行缩进得多。正文的缩进以它的第一行为准，第一行不得为空；正文其余不空的行至少缩进这么多。
8. **流式集合：** `[…]` 和 `{…}`，可以嵌套，写在一行里。各项用 `,` 分开，前后可以有空格；没有结尾多余的逗号，没有空的项。流式映射的一项是键、`:`、一个空格和值。流式序列的一项是一个标量或一个流式集合。流式集合里不带引号的标量不含 `,` `[` `]` `{` `}`。`[]` 和 `{}` 是空序列和空映射。
9. **不带引号的标量**按下表读：

   | 写法 | 读成 |
   |---|---|
   | 空、`~`、`null` | 空值 |
   | `true`、`false` | 布尔值 |
   | `[-+]?(0\|[1-9][0-9]{0,17})` | 整数（至多 18 位） |
   | `[-+]?(0\|[1-9][0-9]*)\.[0-9]+([eE][-+][0-9]+)?`，不超过 32 个字符，值是有限的 | 浮点数 |
   | `.inf`、`-.inf`、`.nan` | 浮点数 |
   | 其余 | 字符串，还要守第 10、11 条 |

10. **必须加引号的：** 落在上表最后一行、又符合下面任何一条的标量：
    - 以数字、`+`、`-`、`.` 开头；例如 `'2026-10-30'`、`'23.1.0'`、`'1e-9'`、`'0x1F'`、`'007'`、`'../lib'`；
    - 不分大小写等于 `y`、`n`、`yes`、`no`、`on`、`off`、`true`、`false`、`null`；例如 `'on'`、`'True'`、`'NULL'`；
    - 或者等于 `=` 或 `<<`。

    键也守这一条。
11. **读成字符串的不带引号的标量：** 不以空格开头，也不以 `-` `?` `:` `,` `[` `]` `{` `}` `#` `&` `*` `!` `|` `>` `'` `"` `%` `@` `` ` `` 中的任何一个开头；不含 `: ` 和 ` #`；不以 `:` 或空格结尾。
12. **带引号的标量：** 单引号里，`''` 表示一个单引号，没有别的转义。双引号里的转义只有 `\0` `\a` `\b` `\t` `\n` `\v` `\f` `\r` `\e` `\"` `\\` `\N` `\_` `\L` `\P`，以及 `\x` 加 2 位、`\u` 加 4 位、`\U` 加 8 位十六进制；别的转义（例如 `\/`）都不许用。带引号的标量和块标量一律是字符串。
13. **注释和空行：** 空的行、只有空格的行、第一个非空格字符是 `#` 的行，都不读。一行里在值之后，至少一个空格再加 `#`，从那里到行尾是注释。块标量的头所在的行上没有注释；块标量的正文里，`#` 是正文。

#### 3.2.4 读和写

- **入口文件不合这些规则的对象不是合格的对象。** 工具报告它，不组装它，不把它当展开树的一部分。按名字列出、拷贝、核对哈希仍然可以。
- **定稿时遇到不合写法的入口文件必须报错，** 不得替作者改写：`on` 是想写字符串还是布尔值，工具不能猜。
- **读的时候，** 工具必须忽略不认识的字段，不得因此拒绝对象。定稿时按类型规格严格检查。
- **类型规格的版本不写在对象里。** 类型规格只做兼容的改动；不兼容的改动用一个新前缀，等于一种新类型（第 10 章）。
- **所有历史版本必须永久可读。** 对象不可变，所以不存在"原地升级格式"。

### 3.3 引用

- **入口文件里，任何层级上，整串是对象名的值就是一条引用。** 只看值，不看键。只是想提到、不想让它成为引用的对象名，写进 `README.md`：不从它的文字里找引用。
- **`lock.json` 里的名字也是引用。** 对象顶层有一个叫 `lock.json` 的文件时，不管对象是什么类型：
  - 它必须是一个 JSON 对象，UTF-8，不超过 1 MiB；
  - 其中任何层级上整串是对象名的字符串值，都是这个对象的引用；
  - 它其余的格式由类型规格定。现在只有验证记录用它（第 9 章）。
- **`members.source.jsonl` 里的成员也是引用。** 对象顶层有一个叫 `members.source.jsonl` 的文件时，不管对象是什么类型，它就是一份成员表：
  - 它是一份按严格的读法合格的来源表（5.1），大小受 3.1 的上限约束，而不是来源表的上限；
  - 头是 `{"toa": "source/1"}`，不多不少；其余每一行都是对象行，没有包含行，因为永远不变的对象不能拉进会变的表；
  - 对象行没有 `removed` 和 `latest`，来源只能是 `git` 来源；
  - 每一行的 `object` 都是这个对象的引用。这份表缓存字段里的名字，例如 `refs` 里的，不是引用；
  - 它还有什么含义，由类型规格定。现在只有冻结库（类型 `lib`）用它，并且要求必须有（第 9 章）。
- **引用必须找得到。** 范围是一份工作区清单展开后列出的对象（8.1）：它包含的各库发布分支上的对象，加上它直接列出的对象。在这个范围里找不到的引用是悬空的，工具必须报告。
- **引用的对象已经删掉、留了删除记录时，** 工具报告它在哪个库删掉了，并给出删除记录里说的（4.2）。
- **库的检查不知道工作区清单。** 它列出不在本库里的引用（6.4 第 9 项），允许不允许由部署定。
- **`history.json` 里的名字不要求找得到。**
- **方向只有一个：后来的指向先有的。** 电路网表指向它实现的模块定义，不反过来。一个模块定义有哪些电路网表，由索引汇总。引用不可能成环：对象的名字取决于它引用的名字。
- **引用锁定整棵树。** 入口文件在哈希里，所以一个对象的名字固定了它引用的每一个对象，一层层到底。
- **放引用的字段怎么起名。** 类型规格给值是引用的字段起名：
  - 只能指一种类型的，用那种类型的前缀，列表加 `s`：`ifc`、`ckt`、`tbs`；
  - 能指几种类型的，或者一个对象在两个角色上引用同一种类型的，用表示角色的英文词：`dut`、`refs`。类型规格写明它允许哪些前缀。

### 3.4 来历：`base` 和 `history.json`

- **`base` 由作者写：** 这个对象直接从哪些对象改来。出同一个设计的下一版、改别人的对象，都写。从零开始的不写这个字段；草稿里写成空列表的，定稿时去掉（7.1）。
- **`base` 的每一项和对象本身前缀相同：** 对象只从同类型的对象改来。定稿和库的检查只看名字就能查。
- **`base` 只说对象是从什么改来的，从不说它取代了谁。** 现在该用哪个，由库在库的清单里给它标 `latest` 来说（5.2、7.5）。
- **引用还是 `base`？** 问一句：这个字段换成指别的，对象说的事还一样吗？换了子电路的电路网表、换了测试用例的验证记录，说的就是另一回事：这样的字段是类型规格定的引用（3.3）。新版电路网表不靠旧版也说同样的事：那就是 `base`。`base` 指的对象随对象一起带上，但不再往下展开（5.2）；`history.json` 里的名字根本不取。
- **一支** 是一个设计的各代：类型相同、`name` 相同，沿 `base` 第一项连起来的对象。没有 `name` 的类型，例如 `evd` 和 `doc`，沿 `base` 第一项的整条来历算一支。可读名去掉代数，就是这一支的名字（6.2）。
  - 移植到别的工艺，或者只为一次仿真做的变体，另起 `name`，自成一支，从第 1 代算起。
  - 别人改了、没改 `name` 的，仍在这一支里。它是不是原来那个库推荐的新版，看哪些库给它标了记号（7.5）。
- **代：** 没有 `base` 的对象是第 1 代。有 `base` 的对象，`base` 第一项和它在同一支里时，代数是那一项的代数加一；不在同一支里时是 1。定稿算出代数，写进 `history.json`，所以一个对象在哪里显示的都是同一代。
  - 代数是给人看的：工具把它写进可读名和标签（6.2）。它从不写进入口文件。两个对象可以是同一代，代数说明不了是谁做的、什么时候做的。
- **`history.json` 由定稿写出：** 对象目录顶层的一个文件。内容是一个 JSON 对象，有两个键：
  - `history`：对象名的列表，最近的在前。列表是 `base` 的第一项，后面接上那一项的 `history`。`base` 有几项时只沿第一项往上记；
  - `generation`：这个对象的代数，从 1 起的整数；`base` 第一项在别的支里时是 1。
  - 有 `base` 的对象必须有这个文件；没有 `base` 的对象不得有，它是第 1 代。
- **写法只有一种：** 两个空格缩进，每个名字一行，以 LF 结尾；和 Python 的 `json.dumps({"history": names, "generation": n}, indent=2)` 写出的内容（键就按这个顺序）后面加一个 LF 逐字节相同。它在对象里、进哈希，不同的工具必须写出同样的字节。例如：

  ```json
  {
    "history": [
      "ckt_cd15342bb4ed1cc1137937195f7cf3c3b8b03af5",
      "ckt_f1ede73af6ba50ae0621e34b2b6f6b946dbf1ff1"
    ],
    "generation": 3
  }
  ```

- **定稿照抄上一代的 `history`、读它的代数之前，** 上一代必须在本机找得到，并且读文件核对相符（7.4）。没有 `history.json` 的上一代是第 1 代。
- **库的检查核对它**（6.4 第 4 项）：写法是那一种；第一项等于 `base` 的第一项；那一项也在本库时，其余各项等于它的 `history`，`generation` 也按上面的算法由它算出；那一项在本库只剩删除记录时，其余各项等于删除记录里的 `history`（4.2）；别的情况下，其余各项和 `generation` 不核对。
- **`history.json` 在对象里，进哈希。** 所以每个对象带着自己完整的来历和代数，链条中间某一环丢了，更早的祖先仍然查得到。
- **它能证明的：** 它点名的、找得到的祖先，内容确定，并且先于它存在。
- **它不能证明的：** 作者是谁，是哪天做的，对象没有借用名单之外的东西。祖先找不到的那一段只是声明的，没法和上一代核对的代数也只是声明的；索引必须把核对过的部分和只是声明的部分分开（8.3）。

### 3.5 外部依赖：对象需要、但不随它发布的文件

公开的对象不带 PDK 的模型和其他受限文件。对象只声明它需要什么；这些文件本身在使用者本机。

- **所有类型用同一套机制；用不用由类型规格定。** 不管什么类型，工艺和别的外部文件都按同样的方式声明。每份类型规格写明这种类型的对象能不能写工艺、写在哪个字段，能不能有 `external`。`0.1` 里，电路网表在 `specifications.process` 里写工艺，电路网表和测试用例可以有 `external`；别的类型两样都不写。
- **对象写的工艺，** 是它的器件来自哪套工艺的模型：一个短名字，例如 `sky130`，形如 `[a-z][a-z0-9_-]{0,39}`。
- **`external`：** 入口文件顶层的一个列表，每项是一个别的外部文件。

  | 字段 | 要求 | 含义 |
  |---|---|---|
  | `name` | 必须 | 在这个对象里怎么称呼它；对象内不重复 |
  | `role` | 必须 | 是哪种文件，例如 `modelfile`、`techfile` 或 `other`：形如 `[a-z][a-z0-9_-]{0,31}` 的一个词。这些词是开放的：工具必须接受它不认识的角色 |
  | `process` | 可以 | 它属于哪套工艺 |
  | `file` | 可以 | 文件名，供人辨认。不含 `/` 和 `\` |
  | `version` | 可以 | 可读的版本标签 |
  | `match` | 可以 | 一组短字符串，文件里必须都出现。用来确认手上的是对的那一份，容忍文件被改名或微调 |
  | `sha256` | 可以 | 整个文件的 SHA-256。只在允许公开这个值、并且要求逐字节相同时写 |

- **一次仿真实际用了哪些模型文件，** 仍然记在验证记录的 `conditions.models` 里：文件名（同样不含 `/` 和 `\`）、`section`、`version`、`match`。每项可以多写 `process` 和 `sha256`。
- **外部文件本身不得进公开的库。**
- **本机映射表**是使用者本机的一份文件，说明每个 `process` 和每个外部文件在本机对应哪个实际文件。它在工作目录里，不进任何公开的库。格式和怎么对上见 7.6。
- **两个对象可以用同一个 `name` 指不同的文件。** `name` 只在一个对象里有意义，所以本机映射表的条目可以多写 `process` 来区分。
- **本标准不要求一棵展开树里的工艺一致。** 组装时工具必须列出整棵树的全部外部依赖，逐个在本机映射表里对上，报出对不上的。两套模型里有同名的器件时怎么处理，是组装工具的事，本标准不规定。

### 3.6 不可变

- 对象的内容定了，名字就定了。任何改动都得到另一个名字，也就是另一个对象。
- 要改一个已有的对象：把它复制成草稿，`base` 指回原来的，改完定稿。

## 4 旁挂文件

对象目录旁边（同一个父目录下）可以有四样名字以对象名开头的东西。它们是旁挂文件：不属于对象，不进哈希。

| 名字 | 是什么 |
|---|---|
| `<object name>.notes/` | 说明目录：这个库对这个对象的补充（4.1） |
| `<object name>.source.jsonl` | 来源表：这个对象和它需要的对象的已知来源（第 5 章） |
| `<object name>.removed.json` | 删除记录：这个对象从这里删掉了（4.2） |
| `<object name>.stamps/` | 时间戳目录：第三方做的、证明这个对象名在某个时间已经存在的证明（4.3） |

- **别的名字不得以 `<object name>.` 开头。**
- **它们必须是普通的目录和普通的文件，** 不得是符号链接。来源表、删除记录各不超过 1 MiB。
- **同一个对象在库里放了几份时，** 每份旁边都可以有自己的旁挂文件。各份的说明是什么关系见 4.1。
- 库里可以有某个对象的旁挂文件而没有那个对象本身。删除记录就是这样；别的旁挂文件这时放在哪都行。

### 4.1 说明

- **一条说明一个文件：** `<object name>.notes/<file name>.md`。文件名守 3.1 第 3 条，必须以 `.md` 结尾，应当写成 `<date>-<short name>.md`（日期加短名），例如 `20261118-erratum.md`。
- **目录里只有直接放在里面的普通 `.md` 文件，** 没有子目录。一份说明不超过 256 KiB。
- **一份说明由对象名加文件名认定，** 和它的说明目录放在库的哪个位置无关。同一个对象在库里有几份、旁边各有说明目录时，同名的说明内容必须相同，合起来算一个说明目录。
- **只增不减：** 一份说明上了发布分支之后，内容不得修改，不得删除。整个说明目录可以跟着对象挪位置。更正的办法是再加一份。例外只有一种：对象删掉时（6.5），它的说明可以一起删。
- **说明是这个库对这个对象说的话。** 同一个对象在原库和 fork 里可以有不同的说明。索引按库分别记。
- **谁写的，** 以加进这个文件的那次提交为准。文件里的署名只是文字。
- **展示说明时，工具必须当作不可信的文本，** 并标明来自哪个库（第 11 章）。
- **撤回、被取代这类给机器读的状态不写在说明里，** 写在库的维护者专管的文件里（6.6）。
- 用途：勘误、澄清、补充。模块定义的文字修正写成一条说明，不出新的模块定义。

### 4.2 删除记录

对象从库里删掉之后（6.5），可以在它原来的位置留一份文件，告诉别人删的是什么、它从哪来、到哪还能找到。

- **本标准不要求留。** 要让库的当前状态里彻底没有一个对象的痕迹，就不留。删除对象的工具应当能写它。
- **文件：** `<object name>.removed.json`。在库里任何位置都算数，应当放在对象原来的父目录下。一个 UTF-8 的 JSON 对象，不超过 1 MiB。
- **字段：**

  | 字段 | 要求 | 含义 |
  |---|---|---|
  | `toa` | 必须 | `"removed/1"` |
  | `object` | 必须 | 被删的对象名，和文件名里的相同 |
  | `commit` | 必须 | 发布分支上含有这个对象的一个提交。工具写删除之前的最后一个 |
  | `path` | 必须 | 对象在那个提交里的路径 |
  | `license` | 可以 | 抄自对象的入口文件 |
  | `label` | 可以 | 给人看的名字，同 5.1 |
  | `base` | 对象有就必须有 | 抄自对象的入口文件 |
  | `history` | 对象有就必须有 | 抄自对象的 `history.json` |
  | `reason` | 可以 | 为什么删。自由文字，不超过 1,000 个字符 |
  | `sources` | 可以 | 别处已知的来源，至多 3 个，只能是 `git` 来源（5.1） |

- **内容从 git 里读，不从工作目录读：** 工具读 `commit` 里 `path` 处的对象，从中抄出上面的字段。
- **它说的必须属实**（6.4 第 8 项）：`commit` 在新提交的历史里；它的 `path` 处是名字所指的对象；`license`、`base`、`history` 和那个对象的相同。
- **可以改，可以删，可以挪位置。** 改过的删除记录按新的一样检查。对象以后又放回来时，删除记录可以留着。
- **用处：**
  - 按名字找的人在库的清单里看到它标着已删除（5.2），到原处读这份记录。
  - `commit` 和 `path` 让人还能从这个库的历史里取到它（7.3）；`sources` 给出别处。
  - `history` 让它的后代的来历仍然能逐环核对（3.4、8.3）。
- 删除记录里的文字是别人写的，按第 11 章对待。

### 4.3 时间戳证明

库可以在对象旁边放第三方做的证明，证明这个对象名在某个时间已经存在。本标准不要求有。

- **目录：** `<object name>.stamps/`，里面只有直接放着的普通文件，每个不超过 64 KiB。文件名守 3.1 第 3 条，应当写成 `<date>-<short name>.<extension>`，例如 `20261124-btc.ots`。
- **盖时间戳的是对象名：** 它的 ASCII 字节，不带换行。给一个名字做的证明，对这个对象放在哪里都成立。
- **扩展名说明文件是哪种证明：**

  | 扩展名 | 证明 |
  |---|---|
  | `.ots` | OpenTimestamps 的证明 |
  | `.tsr` | RFC 3161 的时间戳令牌，DER 编码 |

  可以用别的扩展名。不认识的，工具原样留着。
- **证明随时可以加、换、删；** 例如 OpenTimestamps 的证明锚定之后，换成完整的那一份。库里别的东西都不依赖它们。
- **证明由工具自己核对，** 对着它写明的服务核对。库的检查只看文件的名字、种类和大小（6.4 第 5 项）。证明能说明什么、不能说明什么，见第 11 章。
- **对象在库里放了几份时，** 每份旁边都可以有时间戳目录，合起来算一个。草稿没有时间戳目录，因为它的名字还没定。

## 5 来源表

来源表是一个文件名以 `.source.jsonl` 结尾的文件。它列出一批 TOA 对象，每个对象带一些缓存的信息和零到多个已知来源；它还可以包含别的来源表。对象旁边的来源表、库顶层的库的清单、使用者的工作区清单，都是这一种表。对象目录里面的文件是对象的内容，不管叫什么名字，都不是来源表；只有一个例外：对象顶层的 `members.source.jsonl` 同时也是来源表（3.3），工作区清单可以包含它。

### 5.1 格式

- UTF-8，不带 BOM，换行是 LF。一行一个 JSON 对象。单行不超过 64 KiB。
- **头：** 第一行是 `{"toa": "source/1"}`。
- **其余每行是对象行或包含行。** 有 `object` 的是对象行，有 `include` 的是包含行；两个都有或都没有的行不合格。
- **对象行说一个对象：**

  | 字段 | 要求 | 含义 |
  |---|---|---|
  | `object` | 必须 | 对象名 |
  | `label` | 可以 | 缓存：给人看的名字，例如 `strongarm-comp/wrap-lee.g2`，即可读名（6.2）。自由文字，工具不得从它推出任何东西 |
  | `refs` | 可以 | 缓存：它的全部引用（3.3，含 `base`、`lock.json` 里的名字和 `members.source.jsonl` 里的对象），每个名字一次 |
  | `license` | 可以 | 缓存：它的许可证 |
  | `group` | 可以 | 它的分组（见下） |
  | `removed` | 可以 | 只在库的清单里：`true` 表示这个对象在这个库里删掉了（5.2） |
  | `latest` | 可以 | 只在库的清单里：`true` 表示这个库推荐用这个对象，取代它那一支里之前的各代（5.2、7.5） |
  | `sources` | 可以 | 已知来源的列表 |

  - `label`、`license` 是不超过 256 个字符的字符串。`refs` 是对象名的列表。对象的类型就是它的前缀，表里不另写。
- **包含行把另一份来源表的内容接进来：**

  | 字段 | 要求 | 含义 |
  |---|---|---|
  | `include` | 必须 | 被包含的表的路径：`name/name/…`，每段守 3.1 第 3 条，以 `.source.jsonl` 结尾，不超过 256 个字符 |
  | `sources` | 可以 | 到哪里找这份表。每个来源指向一个根目录（一个库，或一个本机目录），`include` 的路径相对于它。这里的 `git` 来源不带 `path` |
  | `group` | 可以 | 被包含进来的对象放进哪个分组 |
  | `branch` | 可以 | 来源是一个库时，它的发布分支（6.3）；不写就是 `main` |

- **路径相对于什么：**
  - 库里的表（库的清单、它的分卷、对象旁边的来源表）：`include` 和 `local` 都相对于库的根；
  - 别的表：相对于这份表所在的目录。
  - 不写 `sources` 的包含行，被包含的表和这份表在同一处：同一个库，同一台机器，或者按地址取来的同一个提交。
- **展开包含：**
  - 同一份表不管被包含几次只读一次，所以成环也只读一次。至多 8 层。全部表合计的大小上限由工具定。
  - 一份表读不出来，只影响它自己。
  - **每份表里的包含行都跟着走，** 不管表是谁写的。带 `sources` 的包含行按 7.3 的顺序找：本机已有的先用（它的某个 `git` 地址和本机某个库的地址相同，就用那个库），再按来源去取。去不去连某个主机，由工具和使用者定，本标准不规定（第 11 章）。
  - 按地址取来的库的清单里，相对于库的路径的来源指那个库里的位置，等于那个库的 `git` 地址加这个路径。
- **分组：**
  - `group` 是一条分组路径：1 到 4 段，用 `/` 分开，每段守 3.1 第 3 条，合计不超过 128 个字符。
  - 一个对象的分组，是一路包含到它的各条包含行的 `group` 依次接起来，再接上它自己那一行的 `group`。没写 `group` 的那一级不加段。
  - 同一个对象经几条路包含进来，就在每个分组下都出现。
  - 对象的类型不写进分组：工具按前缀分。
  - 分组只给人看。查找、核对、引用、取对象都不看它。
- **每个来源是下面两种之一：**

  | 写法 | 含义 |
  |---|---|
  | `{"git": address, "commit": commit, "path": path}` | 在一个 git 仓库里。`commit` 和 `path` 可以省。不得有别的键 |
  | `{"local": path}` | 在本机的一个目录里。不得有别的键 |

- **`git` 的地址：**

  ```text
  https://主机[:端口]/路径
  ssh://[用户@]主机[:端口]/路径
  ```

  - 主机：用点分开的若干段，每段是 1 到 63 个字母、数字或连字符，不以连字符开头或结尾。写成小写。
  - 端口：1 到 65535。
  - 用户：只在 `ssh` 地址里可以有。`A-Z a-z 0-9 . _ -`，不以连字符开头，至多 64 个字符。
  - 路径：`A-Z a-z 0-9 . _ ~ / -`；各段不为空，不是 `.` 或 `..`。
  - 不带口令、查询串、片段。整个地址不超过 512 个字符。
  - **两个地址相同，** 指主机转成小写、去掉结尾的 `/` 之后整串相同。
- **`commit`** 是 40 位小写十六进制：那个仓库里含有这个对象的任何一个提交。应当写发布分支上沿第一父提交往回数、最早含有它的那一个。
- **`path`** 是对象目录在那个提交里的路径：相对路径，用 `/` 分隔，每段守 3.1 第 3 条。
- **`local`** 在对象行里是对象目录本身的路径，在包含行里是根目录的路径。绝对路径，或者按上面说的相对路径。用 `/` 分隔，不超过 1,024 个字符，不含控制字符和不可见的格式字符。
- **以后的来源形式：** 既没有 `git` 也没有 `local` 的来源，读的时候忽略。
- **缓存的信息都能从对象重新算出**（`label` 和 `group` 除外；`removed` 从删除记录算出）。`latest` 不是缓存的信息：它是库自己的说法。和对象不一致时以对象为准。
- **同一个对象可以出现在几行里，** 读的时候合并。
- **读别人的表时容错，从大到小：**
  - 整份表超过大小上限，或者头的版本不认识：整份忽略。没有头的表按本版本读。
  - 不是 JSON 对象的行、`object` 不是对象名的对象行、不合格的包含行：丢掉这一行。
  - 形状不对的缓存字段、不合格的来源：只丢那一个字段、那一个来源。
  - 每个对象只采用前 3 个来源。不认识的字段忽略。
- **发布分支上的表按严格的读法检查**（6.4 第 6 项）：头是且只是 `{"toa": "source/1"}`；每一行、每个字段、每个来源都合格；每个对象、每条包含行至多 3 个来源；包含行的 `git` 来源不带 `path`；不带 `sources` 的包含行指向同一个提交里的一份表；`removed` 和 `latest` 只出现在库的清单和它的分卷里；本机路径只许是 5.3 允许的那种。表指向哪些地址、包含哪些库的清单，不受限制。

### 5.2 用在哪

| 位置 | 文件 | 内容 |
|---|---|---|
| 对象旁边 | `<object name>.source.jsonl` | 这个对象自己，加上用它所需要的对象 |
| 库的顶层 | `library.source.jsonl`；分卷时还有它包含的 `library.source/` 下的各份 | 这个库里的全部对象，和删掉了、留了删除记录的；可以包含别的清单 |
| 对象里面 | 对象顶层的 `members.source.jsonl` | 一份成员表，随对象一起冻结（3.3）；冻结库在里面列出它的成员和成员需要的对象（类型 `lib`） |
| 使用者的工作目录 | `workspace.source.jsonl`（默认的名字） | 当前设计用到的全部对象：通常是包含几个库的清单（8.1） |
| 别的任何地方 | 任意以 `.source.jsonl` 结尾的文件 | 工具或使用者自己的缓存 |

- **对象旁边的来源表：**
  - 第一行是对象自己。别人把对象和这份表一起取走，就同时拿到了它引用什么、那些对象在哪。发布之前这一行没有来源，发布时补上（5.3）。
  - 其余是用它所需要的对象，按下面算：
    1. 它的全部引用（3.3），`base` 指向的对象也在内。
    2. 对目前得到的、类型要往下展开的每个对象（见下；只经 `base` 引到的不算）：加上它的引用，它的 `base` 除外。对新加进来的对象重复这一步，直到没有新的。
    3. 哪些类型往下展开，由各自的类型规格说。`0.1` 里模块定义、电路网表、测试用例和冻结库往下展开，冻结库沿它的成员表展开；验证记录和文档不展开，工具不认识的类型也不展开。只列对象本身的 `base` 指向的对象；`history.json` 里更早的祖先不列。
  - 这些行也带缓存的信息。取用的人不用先取到任何东西，就知道整棵树有哪些对象、各在哪。
  - 来源的顺序：`git` 来源在前，本机路径在后。发布整理之后每个对象至多留 3 个。
  - 也可以有包含行，例如包含它用到的那些库的清单。
- **库的清单：**
  - 每个对象一行，按对象名排序。来源写 `{"local": path}`：路径相对于库的根（分卷里也是），只能是 `name/name/…` 的形式，每段守 3.1 第 3 条。对象在库里有几份时，写前 3 份的路径。
  - **分组：** 每个对象可以写 `group`，例如按设计分。怎么分由库自己定；样例库取推荐摆法里的模块名（6.2）。
  - **删掉了、留了删除记录的对象**（6.5）也列一行，写 `"removed": true`；来源写删除记录的路径去掉结尾的 `.removed.json`，通常就是它原来的位置。
  - **最新标记：** 对象那一行可以写 `"latest": true`：这个库推荐用这个对象，取代它那一支里之前的各代（3.4）。这个标记只在库的清单和它的分卷里算数，和 `removed` 一样；写在别的来源表里没有意义。
    - 标了的对象在本库里，并且没有删掉。本库里同一支的两个标了的对象，哪一个都不在另一个的 `history` 里（6.4 第 6 项）。从同一个祖先分出来的两个都标了，可以；工具两个都报。
    - 标记随时可以挪走或去掉：出了更好的一代就挪过去，发现有问题就去掉。
  - 别人要在库里找东西，先读这份清单，不用遍历整个库。
  - **包含别的清单：** 维护者可以在库的清单里加包含行，例如按地址包含这个库的对象用到的那些库的清单。使用者只包含这一个库，也找得到整棵树。工具重新写这份清单时，应当保留这些包含行。
  - **太大时分卷：** 对象行放进 `library.source/` 下的若干份表，`library.source.jsonl` 留头、各卷的包含行，和维护者加的包含行。应当按哈希的前两位分成 `00.source.jsonl` 到 `ff.source.jsonl`，查一个名字只读一卷。每卷不超过 16 MiB。`library.source/` 下的每一份都必须被包含到。
  - 对象行是派生的，由维护者一侧的工具写，可以落后。清单和库不一致时以库为准。
  - 投稿不应当改它；维护者合并之后重新写。合并两个分支之后一律重新写，不管 git 有没有报冲突。

### 5.3 本机路径和发布

- **在本机，来源表里可以写本机路径。** 这样它在本地也是缓存，不用每次遍历目录。
- **发布分支上：**
  - 对象旁边的来源表不得有任何 `local` 来源；
  - 库的清单和分卷里的 `local`，只能是 5.2 说的相对于库的路径；
  - 表里写哪些 `git` 地址、包含哪些清单，不受限制。
- **发布时（7.2），工具只动这一次新发布的对象旁边的来源表，** 并且必须：
  1. 去掉全部 `local` 来源。来源全是本机路径的包含行，整行去掉。
  2. 表里凡是在本库的对象（它自己，和它需要的），都补上要发布到的那个库的地址和该对象在库里的路径。已经在发布分支上的对象再带上提交号；这次才发布的没有提交号。
  3. 别处的 `git` 地址照留。
  4. 整理之后，表里不在本库、又一个 `git` 来源都不剩的对象：这一行只留 `object`，缓存的可读名、引用、许可证一律去掉，并列给使用者。公开之后别人按名字找不到它们（第 11 章）。
  5. 这些新对象的 `history.json` 里，不在本库、也不在工作区清单里任何有 `git` 地址的库里的祖先，列给使用者。
- **写出去之前给使用者看什么，由工具定。** 别处的地址会随表公开，`ssh` 地址里的用户名可能是个人账号名。工具可以把要写出去的地址列给使用者，让使用者去掉不想公开的（第 11 章）。
- **本库的地址：**
  - 由使用者指明；不指明时取名叫 `origin` 的远程地址。
  - `https` 地址去掉用户名和口令。主机写成小写。
  - `user@host:path` 这种写法工具不自动改写：在普通服务器上它的路径相对于家目录，改写成 `ssh://` 地址之后可能指到别处。请使用者给出 `https://` 或 `ssh://` 形式的地址。
  - 不合 5.1 的地址（例如本机目录）不补，并告诉使用者。
- **不改已经发布的对象旁边的来源表。** fork 带来的对象，旁边的表仍然指向原库。
- **投稿经合并进入另一个库时，** 那个库的维护者一侧对新进来的对象做同样的整理：补上自己的地址，原来的地址留着。
- **从别处拿来的表里的 `local` 来源：** 只认库里的表里相对于库的路径，它指那个库里的位置，解析出来必须仍在那个库的目录里。其余的忽略。

### 5.4 它是缓存

- 来源表缺了、过期了、写错了，都不影响对象合不合格。
- 工具不得因为来源表缺失或失效而拒绝对象；这条路走不通就换别的路（7.3）。
- 来源表里的任何内容都是别人写的，按第 11 章对待。

## 6 库

### 6.1 库是什么

- **库是一个 git 仓库，指整个仓库。** 这是 `0.1` 版发布和共享对象的方式；对象本身不依赖 git（1.1）。`0.1` 版不定义"仓库里的一个子目录是一个库"。仓库里可以放别的文件，但本节和 6.2、6.4 对整个仓库生效。
- **库不是有含义的一层：** 对象的身份和引用不依赖库，库没有自己的标识。
- **仓库必须用 SHA-1 对象格式。** 建库的工具应当显式指定，读库的工具应当检查。
- **整个库里只有普通文件和目录。** 发布分支上所有成员的模式只能是 `100644` 和 `40000`：没有符号链接，没有子模块，没有带可执行位的文件。
- **`.gitattributes` 只有一份，在库的根，名字就是小写的 `.gitattributes`。**
  - 它必须有一行 `* -text`。
  - 别的行不得设置 `text`、`eol`、`crlf`、`filter`、`ident`、`working-tree-encoding`，不得定义宏（`[attr]`）。
  - 任何别的位置、任何大小写的 `.gitattributes` 都不得出现。在不分大小写的文件系统上，git 会把 `.GITATTRIBUTES` 当成它来读。
- **`.gitmodules` 不得出现在任何位置，** 任何大小写都算。
- **库根可以有：**

  | 文件 | 要求 | 内容 |
  |---|---|---|
  | `library.yaml` | 可以 | `toa: library/1`；展示用的 `name`、`title`、`description` |
  | `library.source.jsonl`，分卷时加上 `library.source/` | 应当 | 全部对象的库的清单（5.2） |

- **库不写自己的地址，也不写自己的发布分支。** 写在库里的地址和分支名，对 fork 和镜像不成立。例外只有发布时补进来源表的那些地址，它们是缓存。
- **库可以不自足：** 库里的对象可以引用别的库里的对象。

### 6.2 摆法

- **工具必须能在库的任何深度找到对象，不得从路径里读出任何含义。** 只有对象目录的名字有意义。
- **同一个对象可以在一个库里放几份，** 都是同一个对象，不算错。对象名只能用作目录的名字。
- **推荐的摆法：**

  ```text
  ifc/strongarm-comp/ifc_945cdda7…/
  ifc/strongarm-comp/ifc_945cdda7….notes/20261007-clk-edge.md
  ifc/strongarm-comp/ifc_945cdda7….source.jsonl
  ckt/strongarm-comp/wrap-lee.g2/ckt_1ec6249c…/
  ckt/strongarm-comp/wrap-lee.g2/ckt_1ec6249c….source.jsonl
  ckt/dyn-latch-cmp/lee-sky130.g1/ckt_f1ede73a….removed.json
  tb/strongarm-comp/tb_offset.g1/tb_ad96a147…/
  evd/strongarm-comp/20261103T1200Z-wrap-off/evd_b7d77959…/
  doc/strongarm-comp/kickback-mitigation/doc_044f932c…/
  lib/toa-official.g3/lib_5d0e7b3a…/
  library.source.jsonl
  ```

  - 第一级是类型目录，名字就是前缀；第二级是模块名；第三级是其余的可读名；最后是对象目录。模块定义没有第三级；不讲任何模块定义的文档，以及冻结库，没有模块名这一级。
  - 可读名由工具在新建对象时按字段和代数（3.4）拼出，之后不检查它和字段是否还一致。`wrap-lee.g2` 里的 `g2` 就是第 2 代。
- **对象之外的每一级名字，** 守 3.1 第 3、4 条，只是允许以点开头（`.gitattributes`、`.gitignore`、`.github/`）。
- **路径预算：**

  | 哪一段 | 上限 |
  |---|---|
  | 对象目录之前的路径，连同结尾的 `/` | 60 个字符 |
  | 对象名 | 49 个字符（前缀至多 8，加下划线，加 40） |
  | 对象内的路径（3.1），连同前面的 `/` | 81 个字符 |
  | 合计：库内任何文件的路径 | 190 个字符 |

- **Windows：** git 默认设置下，完整路径到 260 个字符就检出失败，而且是整个库检不出来。工具克隆库时应当为该仓库打开 `core.longpaths`。

### 6.3 发布分支和"已发布"

- **发布分支是哪一个，由用这个库的人说：** 包含这个库的包含行的 `branch`（5.1、8.1），没写就是 `main`。使用者自己的清单里写的优先。库的维护者对自己的库也是这样说。
  - 分支名：`A-Z a-z 0-9 . _ / -`，以字母或数字开头，至多 100 个字符，不含 `..`，不以 `/` 或 `.lock` 结尾。
- **一个对象在某个库里已发布，** 指它的目录在该库发布分支最新的提交里，也就是别人现在能从这个库拿到它。
- **在一份检出里怎么判断：**
  - 这个分支有远程跟踪引用（`refs/remotes/origin/<branch>`）时，以它为准。本地提交了、还没推送的对象不算已发布。
  - 没有远程跟踪引用的仓库（库本身，或没有远程的本机库），以本地分支为准。
  - 仓库有远程跟踪引用、但没有这个分支的（例如这个分支从没推送过），也以本地分支为准。这时只在本机提交的对象也算已发布，这样偏安全：它们不能取消定稿（7.1）。工具应当告诉使用者这个分支没有远程跟踪引用。
  - 仓库里有提交、却没有这个分支，是错误，不得当成"什么都没发布"。
- **"在这个库里"只有这一个判据。** 能用这个库的地址按名字取到，不等于在这个库里：未合并的分支、被丢掉的提交里的对象也可能取得到。
- **把对象放上发布分支的那个提交应当签名，** 用 git 自带的 SSH 或 GPG 签名。做提交的工具按使用者的 git 设置签名。核对通过的签名说明是谁在那个提交里把对象放进了这个库；它不说明对象是谁写的，提交的日期也仍然是提交者自己写的（第 11 章）。
- 来源表里的 `commit` 可以用来核实出处：它是发布分支的祖先，并且那里 `path` 处的 tree 号等于对象的哈希。

### 6.4 库的检查

- **库的维护者必须在把发布分支移到一个新提交之前，对它做下面的检查。**
- **基准**是发布分支当前的头。新提交必须是它的后代；不是的话，历史被改写了，拒绝。
- **删除**（6.5）不受限制：不用另交删除的名单，也不要求留删除记录。
- 检查只需要 git 的目录列表和少量小文件。读每个文件之前先看大小。目录列表边读边数，一超过部署定的上限就拒绝，不要读完再数。
- **读不出目录列表的提交，一律拒绝。**

1. **仓库和全库：** 仓库是 SHA-1 格式；`.gitattributes` 和 `.gitmodules` 守 6.1；全库没有符号链接、子模块、带可执行位的文件；新提交是基准的后代。
2. **每个名字是对象名的目录：**
   - 它的 tree 号等于名字里的哈希；
   - 按目录列表重新拼出的规范 tree 号也等于它（7.4）；
   - 它是合法的对象树（3.1），列出的每个文件确实存在、确实是文件；
   - 同一个对象有几份时，每一份都这样查；
   - 对象名不出现在不是目录的东西上。
3. **没有草稿名**（2.4 列的几处）。
4. **每个对象的文件：** `toa.yaml` 合乎 3.2 的写法，公共字段合格，`type` 等于前缀；`lock.json` 和 `members.source.jsonl`（有的话）合乎 3.3；`history.json` 是那一种写法，和 `base` 相符，上一代在本库时它的 `generation` 也和上一代相符（3.4）；`base` 的每一项和对象本身前缀相同。
5. **对象之外：** 每一级名字的规则；路径预算；以"对象名加点"开头的名字只有四种：`.notes` 目录、`.source.jsonl` 普通文件、`.removed.json` 普通文件和 `.stamps` 目录，目录里只有直接放着的普通文件，每个不超过 64 KiB，名字守 3.1 第 3 条（4.3）。
6. **来源表**（对象目录之外、名字以 `.source.jsonl` 结尾的所有文件；对象目录里面的文件是对象的内容，不是来源表；对象顶层的 `members.source.jsonl` 由第 4 项检查）：大小不超限；按严格的读法合格（5.1）；对象旁边的表没有 `local` 来源；库的清单和分卷的 `local` 是相对于库的路径；不带 `sources` 的包含行指向这个提交里的一份表；`library.source/` 下的每一份都从 `library.source.jsonl` 包含到，不超过 8 层。`latest` 标记守 5.2：标了的对象在本库里、没有删掉，本库里同一支的两个标了的对象，哪一个都不在另一个的 `history` 里。表指向哪里不查。
7. **说明目录：** 只有直接放在里面的普通 `.md` 文件，每份不超过 256 KiB；同一个对象几份旁边同名的说明内容相同；和基准相比，已有的说明（按对象名加文件名认）没有被改、没有被删，删掉了的对象的说明除外。
8. **删除记录属实：** 每份新加的或改过的删除记录合乎 4.2 并且属实。不要求消失的对象留记录，也不要求已有的记录一直留着。
9. **列出不在本库里的引用。** 公开的库允不允许，由部署定。

- 一个对象出错只报它自己，不得让别的对象查不下去。

### 6.5 删除

- **本标准不限制删除对象。** 删掉的是这个库里的这一份。对象名不变，别人对它的引用、各处 `history.json` 里的记录、这个库 git 历史里的那一份，都还在。
- **删除记录不是必须的**（4.2）。留了，别人还能顺着它找；不留，这个库的当前状态里就没有它的痕迹（git 历史里仍有，见下）。删除对象的工具应当能在它原来的位置留一份；库的检查只核对留了的记录属实（6.4 第 8 项）。
- 删除时，它旁边的来源表一起删（留删除记录的，表里别处的 `git` 来源抄进记录）；说明目录和时间戳目录可以留着，也可以一起删。
- 库的清单里：留了删除记录的，它那一行标上 `removed`（5.2）；没留的，这一行去掉。
- **撤回一个对象是给它做标记**（6.6），不是删掉它：撤回的对象还在，只是这个库说不要再用。
- **删除不等于别人拿不到。** 推上公开库的东西应当按已经公开对待：git 历史里还有它，别人也可能早已拷走。确实要从历史里抹掉（例如误传了受限内容），只能改写历史，库的检查会拒绝（第 1 项），由部署在本标准之外处理。
- 来源表是缓存，任何时候都可以删、可以重新写。

### 6.6 库里其他会变的文件

撤回、被取代这类状态，别名，工艺登记，收稿规则，放在库的维护者专管的文件里。它们的格式不在 `0.1` 版的范围内。它们只对本库说话：同一个对象在两个库里，各库说各库的。

## 7 操作

### 7.1 定稿和取消定稿

定稿把草稿变成对象。它在提交之前做，可以重复做。

- **要么全部做完，要么什么都不改。** 中途任何一步出错（包括目录正被别的程序占用、改名失败），已经改过的文件和目录名必须恢复原样。

1. **分清四种目录：**
   - 草稿名的目录：这次要定稿的；
   - 对象名的目录，内容和名字相符：不动；
   - 对象名的目录，不是合法的对象树，或内容和名字不符：**报错并停止，不改任何名字。** 这可能是一份被改动过的别人的对象；
   - 同一个对象名出现几次：每一份分别按上两条处理（6.2）。
2. **把草稿按依赖排序，** 被点名的在前。一个草稿依赖它点名的每一个草稿，`toa.yaml`、`lock.json` 和 `members.source.jsonl` 里的都算。成环就报错。
3. **按这个顺序，对每个草稿：**
   1. 用本次已经得到的对象名换掉草稿名：`toa.yaml` 里的每个值、`lock.json` 里的值，以及 `members.source.jsonl` 里的值。换完之后还有草稿名形式的值，报错。
      - **只换值的那几个字符。** 引号、缩进、注释和文件的其余字节一律不动。草稿名和对象名都只用小写字母、数字、下划线和连字符，放在哪种写法的标量里都不用转义，所以换法是唯一的。
      - **所以草稿里的草稿名必须照原样写：** 在 `toa.yaml` 里写成一行里不带转义的标量；在 `lock.json` 和 `members.source.jsonl` 里写成不带转义的 JSON 字符串。草稿名写成别的样子，定稿报错。
      - **不需要改的文件原样不动，** 一个字节都不改。
   2. 有 `base` 的，写出 `history.json`（3.4）。`base` 的第一项在本机找不到，或核对不符，报错。没有 `base` 的，删掉草稿里的 `history.json`。草稿可以写 `base: []`，这时它必须是顶层单独的一行；定稿删掉这一行，其余字节不动。
   3. 检查：合法的对象树；入口文件的写法和公共字段；`type` 等于前缀；类型规格的要求。工具不认识的类型照样定稿，只是做不了最后一项。
   4. 算哈希，**两种办法都算：** 按 2.2 读文件算一遍；按这个仓库真实的设置交给 git 算一遍（忽略规则、属性、文件模式都生效，例如用一个临时索引 `git add` 再 `git write-tree`）。两者不同就报错，并说出原因（常见的是有文件被 `.gitignore` 忽略、带了可执行位、换行被转换）。
      - **不在 git 仓库里的草稿**只算第一遍。工具必须告诉使用者第二遍没做。对象以后提交进库时，发布之前的核对（7.2）和库的检查（6.4 第 2 项）会查出第二遍本来要查出的问题。
   5. 把目录改名成 `<prefix>_<hash>`。旁边的说明目录和来源表跟着改名。新名字已经被占用时报错（例如同一个目录下两个内容相同的草稿）。库里别处已经有这个对象不算错。
   6. 写出它的来源表（5.2）。
4. **定稿不需要任何保存下来的对照表。** 草稿之间用草稿名互相引用就够了。

- **取消定稿：** 定稿之后、发布之前想再改，先把对象改回草稿。
  - 工具必须同时把引用它的、同样还没发布的对象一起改回草稿（一层层往上，直到没有），并把它们之间的名字换成草稿名，`toa.yaml`、`lock.json` 和 `members.source.jsonl` 都换，换法同第 3 步第 1 小步。旁挂文件跟着改名。
  - 草稿名由工具取。已经有同名的东西时报错。要改回的对象里有哪个在库里不止一份，也报错：请使用者先删掉多余的。
  - 已发布（6.3）的对象不得取消定稿。
- **提交钩子是可选的，只做检查：** 发现草稿名或名字对不上的目录就拒绝提交。不改任何名字。
- **真正的保证是 6.4 的库的检查，** 不是使用者本机的工具。

### 7.2 发布

把定稿好的对象放上发布分支之前，工具必须：

1. 确认没有草稿；这一次新发布的对象逐个读文件核对（7.4）；跑一遍 6.4 里能在本机做的检查。
2. 按 5.3 整理这一次新发布的对象旁边的来源表。没有的补一份。
3. 重新写库的清单（可以由维护者一侧在合并之后做）。

- **这些整理在提交里完成。** git 的推送不能改动已有的提交，所以"推送时再去掉本机路径"做不到；能做的是推送之前再检查一次，不合格就不推。

### 7.3 取对象

取对象是按名字拿到一个对象的文件。

- **到哪里找，依次：**
  1. 本机已有的：本机的库、本机的缓存，按名字找。**用之前必须读文件核对**（7.4）：本机的拷贝也可能被改过。
  2. 工作区清单给出的：它直接列的对象，和它包含的各库。有库的清单的，先读清单，再取对象。
  3. 手里的来源表给出的地址。
- **连不连某个主机，** 由工具和使用者定，本标准不规定（第 11 章）。
- **从一个 git 地址取，步骤是固定的：**
  1. **先看名字。** 要取的名字必须整串是对象名，不是就什么都不做。每个对象至多试 3 个来源。
  2. **不合格的来源**（5.1）丢掉，不交给 git。
  3. **调 git 时：** 地址放在 `--` 之后，使它不可能被读成选项。git 不得弹出输入；工具要问使用者，就在调 git 之前自己问。不跟随重定向。设超时，超时后 git 和它起的进程一起结束。只允许 `https` 和 `ssh` 两种传输（git 的 `GIT_ALLOW_PROTOCOL`）。不在本机留下指向这个地址的远程设置。
     - **凭据**（使用者的 git 凭据、凭据助手、钥匙）用不用，和连不连主机一样，由工具和使用者定：使用者没同意过的主机，工具不得用。自动运行的服务用什么，由部署定（第 11 章）。
  4. **让 git 检查收到的东西**（`fetch.fsckObjects`）。
  5. **写盘之前**先读目录列表，按 3.1 检查每条路径的每一级，以及模式、大小、个数。目录列表边读边数，超过一个合格对象可能有的条数就停。
  6. **把文件按原始字节写进一个临时目录。** 每个文件写之前确认目标路径在临时目录之内。写完按 2.2 重算哈希，再查入口文件的写法和 `type` 等于前缀。都过了才改名到位；任何一步不过，就把临时目录删干净。
  - 第 4 步和第 5 步各自独立成立：不得因为做了其中一步而省掉另一步。
- **旁挂文件、库的清单和整个库也走这些步骤。**
  - 取一份清单（5.1 的包含行），取那个分支最新的提交，只读里面的那一份表，先看大小再读。
  - 取对象旁边的说明和来源表，用来源里的 `commit` 和 `path`。
  - 克隆整个库时先不检出，按 6.4 第 1、5 项查过目录列表再检出；或者一直不检出，只读 git 里存的内容。说明目录里的一个符号链接，检出之后会指到库外。
- **按名字直接取：** `git fetch <address> <hash>` 只取这一个目录。这需要 git 的 v2 协议（git `2.26` 起是默认），或服务器允许按任意对象号取。
- **退路：** 按名字取不到时，用来源里的 `commit` 和 `path` 取；再不行就克隆整个库。库里只剩删除记录时，按记录里的 `commit` 和 `path` 或它的 `sources` 再试（4.2）。部分克隆的过滤条件被服务器忽略时，工具必须告诉使用者这次是完整克隆。
- **一次取几个：** 要取多个对象时，每个地址一次请求。其中一个名字对方没有会让整次失败，这时拆开重试，并在本次运行里记住失效的地址。
- **留住：** 取回的对象应当落成文件。只放在 git 的存储里时必须建引用，否则会被 git 清理掉。
- **大文件：** 对象带大文件时分两步取，先取目录，再只取本机缺的文件。
- **旁挂文件不随对象来。** 按名字取到的只有对象目录。
- **离线传递：** 用 `git bundle`，或者直接拷对象目录。收到之后一律读文件核对。
- 取到的对象只证明内容是名字所指的那一份。它在不在某个库里，按 6.3 另行判断。

### 7.4 核对

| 办法 | 做什么 | 什么时候成立 |
|---|---|---|
| 读文件核对 | 按 2.2 重算哈希，和目录名比；查 3.1；查入口文件的写法（3.2）；查 `type` 等于前缀 | 任何地方。这是最终的依据 |
| 读目录列表核对 | 只读 git 的目录列表：存的 tree 号等于名字；按列表重新拼出的规范 tree 号也等于它；成员的模式和名字合规 | 仓库是经 git 传输得到、并且开了 `fsckObjects` 的，或先做过 `git fsck`。直接拷来的仓库不成立 |

- **重新拼：** 把列表里的文件按 2.2 对目录的规则拼成树，文件的哈希用列表给的，不读文件内容。存的树里模式多写了 0、成员没排序、成员名带 `/`、有空目录时，拼出来的号和存的不同。
- **什么时候必须核对：**

  | 场合 | 办法 |
  |---|---|
  | 从别处取来的对象，改名到位之前 | 读文件核对（7.3 第 6 步） |
  | 本机已有的对象：用它之前（展开、组装、列外部依赖），照抄它的 `history` 之前，发布它之前 | 读文件核对 |
  | 库的检查：新提交里的每个对象 | 读目录列表核对，加 6.4 第 4 项 |
  | 索引收录一个对象 | 读目录列表核对，加入口文件的检查 |

- 导出或拷贝对象时必须按原始字节写。会按本机设置转换换行的办法，例如 `git archive <hash>`，不得使用。
- 在 git 工作目录里，读文件核对不符而 git 报告没有改动时，原因多半是检出时被转换，或目录里多了杂物文件，不是对象被改。

### 7.5 更新和订阅

- **库的 git 历史就是它的广播。** 比较前后两个提交的对象名集合，得到新增的和消失的；消失的必须报告，留了删除记录的一并给出记录的内容。工具记住每个库上次看到的提交；上次的提交不是新提交的祖先时，必须报告并重读整个库。
- **一个被引用的对象 P 有了新版 N，** 指下面几条都成立：
  - 使用者读的某个库，在它的库的清单里给 N 标了 `latest`（5.2）；
  - N 的 `history` 里核对过的部分（8.3）含有 P；
  - N 和 P 在同一支里（3.4）。
- **N 和 P 的 `ifc` 不同时，** 模块定义变了，工具必须说明。跟进时，和引用一起的 `ifc` 也要一起换，例如 `uses` 里一项的 `ifc` 和它的 `ckt` 一起换；端口变了的，网表也要改。
- **哪些库这样说，由使用者掂量。** 工具报告哪些库给 N 标了记号，以及 N 和 P 在哪些库的发布分支上；不替使用者下结论说 N 是谁出的。
  - 记号是一个库自己的说法。fork 出来的库带着原库的全部对象，也可以随意标，所以 fork 库里的记号不说明 N 出自原作者；使用者按自己信哪些库来判断。
  - 公开平台可以再加一条：两者由同一个核实过的账号加入。
  - 不得用对象自己写的 `author` 来判断。`name` 只说明一个记号管到哪几代（3.4）：别人起同样的名字，也只能在自己的库里标，使用者看得出是哪个库。
- **没有哪个库标记的后代，** 只在使用者要看时列出，不当作新版推送。
- **跟进是自愿的，逐层的。** 引用方复制成草稿、改引用、定稿，得到它的新版；已有的验证记录留在旧版上。跟进一处，上面每一层引用方都要出一个新对象；工具应当先告诉使用者一共会产生几个。
- **验证记录不能走捷径：** 验证记录测的是它那个电路网表原样的展开树，不能用某个子模块的别的版本代替树里写的那个（`evd` 类型规格）。

### 7.6 组装

组装把一个电路网表连同它的展开树变成一组可以直接仿真的文件。

- 按引用展开整棵树；同一个对象只展开一次；每个对象展开之前先核对（7.4）。
- 子电路重名时由工具改名。
- 列出整棵树的全部外部依赖（3.5），在本机映射表里逐个对上，核对 `match` 和 `sha256`，写出 include 模型文件的那几行。
- 写出 `lock.json`：整棵树每个对象的名字，和类型规格指定的那些文件各自的 SHA-256（第 9 章）。
- **本机映射表：** 工具应当默认在工作区清单所在的目录里找 `local-files.yaml`；使用者可以指定别的文件。工具还有没有一台机器上所有工作区共用的一份、放在哪，由工具定。它的格式（示意）：

  ```yaml
  toa: local-files/1
  process:
    sky130:
      release: <本机这套模型的发行名>
      models:
      - file: <本机路径>/design.scs
      - file: <本机路径>/models.scs
        sections: {typical: tt, slow: ss, fast: ff}
  external:
  - name: <对象里 external 的 name>
    process: <可以不写：只对这套工艺的对象生效>
    path: <本机路径>
  ```

- **怎么对上：**
  - 对象写的工艺（`0.1` 里是电路网表的 `specifications.process`），在映射表的 `process` 下按名字找。
  - 对象的每个 `external`，和映射表的 `external` 里 `name` 相同的条目对上；条目写了 `process` 的，还要和这个外部文件的 `process`（没写的话，和它所在对象写的工艺）相同。
  - `match` 里的每个字符串都必须在它的文件里出现。
- 工具不得自动执行对象里带的命令，不得自动安装对象里列的依赖（第 11 章）。

## 8 工作区清单和索引

### 8.1 工作区清单

工作区清单是使用者工作目录里的一份来源表（5.1），列出当前设计用到的全部对象。默认叫 `workspace.source.jsonl`。

```text
{"toa": "source/1"}
{"include": "library.source.jsonl", "group": "official", "branch": "main", "sources": [{"git": "https://example.org/rnl-hub-lib.git"}, {"local": "../checkouts/rnl-hub-lib"}]}
{"include": "library.source.jsonl", "group": "mylib", "sources": [{"local": "../mylib"}]}
{"include": "team/shared.source.jsonl", "group": "team"}
{"object": "ckt_…", "group": "mine/blocks", "sources": [{"local": "blocks/ckt_…"}]}
```

- **用一个库，就是包含它的库的清单。** 包含行的 `sources` 说库在哪：别人也能用的地址，和本机检出的位置。本机有检出时，工具可以直接遍历那个库，代替读它的清单（清单是缓存，5.2）。
- 库的清单又包含别的库的清单时（5.2），那些库也进来。它们的地址和工作区清单里某个库的地址相同时，用本机的那个（7.3）。
- 也可以包含工作目录里别的表，或者直接列对象（上例第 4、5 行）。
- **冻结库也这样用：** 一行包含行，`include` 写它的成员表在库里的路径，例如 `lib/toa-official.g3/lib_5d0e7b3a…/members.source.jsonl`（类型 `lib`）。工具也可以按名字展开一个冻结库。
- **范围：** 展开之后列出的全部对象构成一个范围，引用在这个范围里按名字找（3.3）。
- **分组：** 包含行的 `group` 一般写库的名字，库的清单里的 `group` 再分一层（例如设计），类型那一层按前缀分。使用者看到的是 `official/strongarm-comp/circuits/…` 这样的层次，而不是平铺的对象。
- **使用者自己写的表和别人写的表，读法一样。** 工具只在去连主机时可以区别对待：样例库的工具去连使用者自己写进清单的主机不再问，别的主机先问。这是那个工具的做法，本标准不规定（第 11 章）。
- 工作区清单里有本机路径，不应当进公开的库（5.3）。

### 8.2 索引是什么

- 索引是派生数据：把一份工作区清单包含的库读一遍得到的东西。丢了可以重建。
- 库的清单是各库交给索引的现成材料。索引可以直接用它，但清单是缓存；要求可信的场合（平台收录对象），必须对着对象本身核实。
- 索引回答三类问题：
  - **反查：** 谁直接引用了它；谁的 `base` 写了它。
  - **在哪、什么时候：** 它在哪些库的哪个路径（同一个库里可以有几个）；各库的发布分支上第一次出现它的是哪个提交、哪天。
  - **状态：** 各库对它的说明；各库的删除记录、`latest` 标记、撤回和取代标记。

### 8.3 索引的要求

- **只存直接关系。** "它的全部后代"在查询时沿 `base` 一步步走出来。
- **`history.json` 分两部分记：** 从对象出发，沿 `base` 逐环找得到、并且每一环的 `history` 都对得上的部分，是核对过的部分；之后的是只是声明的部分。`generation` 在 `base` 第一项找得到、并且和它对得上时算核对过的，否则只是声明的。`history` 或 `generation` 和找得到的 `base` 链对不上的对象，标为不合格。
- **某一环在它的库里只剩删除记录时，** 对着删除记录里的 `history` 核对；删除记录本身先按 4.2 核实。
- **反查和订阅只用核对过的部分。**
- **`base` 找不到的对象另放一栏：** 记下它的 `history` 里最近一个找得到的祖先，标明"这是对象自己声明的，中间有缺"。这一栏只给人看，不混进上面的反查，也不用来判断新版。
- **日期：** 取发布分支上沿第一父提交数、最早含有它的那次提交的提交者日期。提交人和日期是提交者自己填的。那次提交签了名的（6.3），索引记下签名人和签名是否核对通过。公开平台应当另记它首次收录这个对象的时间和核实过的账号。
- **有相同的文件、却没声明来历。** 对象 O 里有一个文件，和另一个对象 P 里的某个文件逐字节相同（2.2 的两个哈希相等），并且下面四条都成立时，索引应当指出来。在本机检查对象的工具，在它找得到的对象范围里也应当这样提示。提示给出最早的那个 P 和是哪几个文件；也可以列出别的对象，索引还可以在 P 的页面上说哪些后来的对象里有它的文件。这只是给人看的提示：绝不是判对象不合格的理由，也不算对象的问题。
  - **P 比 O 早。** 同一个库里，按两者在发布分支上沿第一父提交首次出现的先后定。不在同一个库里时，工具用它有的日期，例如它首次见到各对象的那天、上面说的日期，并说明是按什么定的；提交日期是提交者自己写的。分不出先后时，例如两者首次出现在同一次提交里，不提示。
  - **作者不同。** 两边的 `author`（3.2.1）去掉首尾的空白、中间每一段连续空白算一个空格、不分字母大小写后再比。只有一边写了 `author` 时，算不同；两边都没写时，不提示。电路网表的 `origin` 里的 `authors` 不参与。
  - **两者没有关系。** 谁都不在对方的 `base` 或 `history`（3.4）里，谁都不引用对方（3.3）。
  - **这个文件不在略过之列。** 下面这些文件不比：
    - 许可证全文：名字以 `LICENSE` 或 `COPYING` 开头的文件，以及目录 `LICENSES/` 下的文件；
    - `history.json` 和 `lock.json`，它们由别的对象推出：从同一个 `base` 改出来的两个对象，`history.json` 相同；
    - 不到 256 字节的文件，空文件也在内；
    - O 的某个文件，也在 O 的来历（它的 `base` 和 `history`）里某个找得到的对象中：O 已经声明了它从哪里来，例如两个对象从同一个祖先改出来时；
    - 很多互不相关的对象都有、或者很多不同作者的对象都有的文件，例如模板、常见的包含文件。多少算多由工具定，并应当写进它的文档。
- **对照值：** 索引给每个合格的对象记下 2.2 的对照值。同一个名字在两个位置得到的对照值不同时，报警。
- **一个对象读不出来，只记它自己；一个库读不出来，只记这个库。** 别的照常。
- **索引的布局不在 `0.1` 版的规定之内。** 应当分片，使解析一个名字只读一个小文件。写索引的工具把格式写进自己的文档，作为它自己的、以后可能变的格式。平台的索引和收录记录的格式也留给以后（附录 B）。
- 发布的索引不得带本机路径。

## 9 类型

| 类型 | 前缀，也是 `type` 和类型目录 | 引用字段 | 推荐的可读名 | 类型规格 |
|---|---|---|---|---|
| 模块定义 | `ifc` | 无 | `ifc/<interface name>/` | `types/en/ifc.md` |
| 电路网表的一代 | `ckt` | `ifc`；`uses.<subcircuit>.ifc` 和 `.ckt` | `ckt/<interface name>/<name>.g<generation>/` | `types/en/ckt.md` |
| 测试用例的一代 | `tb` | `ifc` | `tb/<interface name>/<name>.g<generation>/` | `types/en/tb.md` |
| 验证记录 | `evd` | `dut`、`tbs`；`lock.json` 里的名字 | `evd/<interface name>/<record label>/` | `types/en/evd.md` |
| 文档 | `doc` | `refs` | `doc/<interface name>/<short name>/` | `types/en/doc.md` |
| 冻结库 | `lib` | `members.source.jsonl` 每一行的 `object` | `lib/<name>.g<generation>/` | `types/en/lib.md` |

- **前缀就是类型的名字：** `type` 写它，推荐的类型目录也用它。表里的中文名只给人看。
- **表里的引用字段只是说明。** 什么算引用由 3.3 定，和类型无关；类型规格怎样给这样的字段起名，也在 3.3。
- 所有类型的对象都可以有 `base`、`title`、`description`、`tags`（3.2.1）。
- **类型规格**写明这种类型的入口文件有哪些字段、对象里带哪些文件、定稿时对这种类型查什么。它分两部分：正文 `types/en/<prefix>.md`，和用 JSON Schema 写的字段定义 `types/<prefix>.schema.json`。字段定义是"有哪些字段、哪些必填、取值是什么形式"的唯一来源；正文写 JSON Schema 表达不了的规则。
- **类型规格和本标准的各章分开放，** 随本标准的每次修订一起发布。类型规格只做兼容的改动（第 10 章），所以每个前缀只有一份现行的规格，它写明自己需要哪些版本的公共规则（第 2 到 8 章）。
- **前缀 `lay` 留给版图。** 加它之前要先定大文件怎么放：对象不得依赖 git 的过滤器（6.1），所以大文件要么直接放进对象，要么对象里只放一份写明大文件哈希和大小的小文件。
- **增加一种类型，** 是写一份类型规格并在本表登记一行。登记是为了不重复用前缀；没登记的类型，工具照样核对 `type` 等于前缀。第 2 到 8 章不用改。
- **永远不登记为前缀的词：**
  - Windows 的设备名：`con`、`prn`、`aux`、`nul`、`com0` 到 `com9`、`lpt0` 到 `lpt9`。推荐摆法的类型目录就用前缀命名（6.2），Windows 上不能有这样的目录；
  - YAML 可能读成字符串以外的词：`y`、`n`、`yes`、`no`、`on`、`off`、`true`、`false`、`null`；
  - TOA 自己的词：`check`、`verify`、`note`、`source`、`lock`、`library`、`latest`、`removed`，以及入口文件里不按前缀起名的字段名，例如 `type`、`name`、`base`、`files`、`uses` 和 `process`；
  - 文件格式的名字：`lef`、`def`、`gds`、`oas`、`spef`、`sdc`、`upf`；
  - 在别处另有意思的词：`cell`、`view`、`module`、`entity`、`component`、`model`、`net`、`mod`；
  - 本标准的草稿给类型用过的名字：`ip`、`imp`、`ver`。
- **以 `x` 开头的前缀** 留给私有和实验用的类型，永远不登记。

## 10 版本和演进

- **类型规格的版本不写在对象里。** 一种类型的规格只做兼容的改动：加可以不写的字段，放宽取值。不兼容的改动用一个新前缀，等于一种新类型；旧前缀的对象照旧合格，工具都要继续读。
- **公共规则（第 2 到 8 章）跟着本标准的版本走。**
  - `0.x` 期间可以改，改了就可能让已有的样例对象不再合格。
  - `1.0` 之后，已经合格的对象和库不得因为本标准的修订变成不合格：上限只放宽不收紧，保留的名字不再增加，必须加引号的写法不再增加。
- **哈希算法定在名字里。** 换算法时新对象用 2.1 保留的那种形式，旧名字不变。同一份内容的新旧两个名字是不是同一个对象，由一张别名表说明，不靠推断。新对象用旧名字引用一个对象时，这条引用的强度仍是旧算法的。
- **旧工具遇到新东西：** 不认识的前缀，原样保留，不解释内容（`type` 等于前缀照样核对）；不认识版本的来源表，整份忽略；保留形式的名字，不进入、不改动。
- **本标准自己的版本**写在来源表的头里，以及删除记录、`lock.json` 和 `library.yaml` 的 `toa` 字段里。

## 11 安全上必须写明的事

- **名字保证的只有一件事：** 内容是名字所指的那一份。它不保证有人审过，不保证作者是谁，不保证对象在某个库里。
- **取用别人的对象就是执行别人的代码。** 测试用例带分析脚本和仿真命令；依赖清单可以指向任意软件源；网表里的 Verilog-A、Verilog 和仿真器的控制语句可以写文件、调系统命令。
  - 工具不得自动执行对象里带的命令，不得自动安装对象里列的依赖。
  - 没有审过的对象应当在容器或虚拟机里仿真。
  - 一棵树里有没审过的对象时，工具在组装和运行之前应当把它们列给使用者。
- **对象和旁挂文件里的文字是数据，不是指令。** 给 agent 用的工具和文档必须写明这一点。
- **展示说明、README、文档时，** 工具不得自动加载它们指向的外部资源（图片、脚本、链接预览）。
- **来源表、说明、库的清单、删除记录都是别人能改的。** 读它们时按 5.1、4.2 校验，取对象时按 7.3 的步骤。
- **来源表可以写任何地址，包括内网地址和本机地址，也可以包含任何别的清单。** 本标准不限制表指向哪里，也不规定工具去不去连某个主机，这由工具和使用者定。要知道的风险：
  - 跟着别人的表去连，等于让写表的人替你选连哪里：可能是你内网里的服务，也可能只是借此知道你在用什么。交互的工具一般在连一个没连过的主机之前问使用者。
  - 自动运行的服务（平台、CI）没有人可问。它按表里的地址去连，就可能被人引去连内网的服务。它能连哪些主机，由部署定。
- **凭据。** 对别人的表给出的地址用使用者的凭据，等于把凭据送到那份表选的主机，还可能取到私有的内容。交互的工具只对使用者同意过的主机用凭据（7.3）。持有凭据的自动服务，可能被人引去取私有的对象，再放进公开的输出；它用哪些凭据、对哪些主机用，由部署定。
- **地址不是身份。** 库的地址可以易主。易主之后新主人换不掉已经被点名的内容，但能发布"新版"、改说明。
- **依赖别的库的对象时，** 库应当把它们复制进自己或镜像里（对象名不变），不要只留一个地址。
- **时间的证据。** 对象里没有日期，提交的日期是提交者写的，可以往前改。对象某天以前已经存在，只能由别人证明：
  - **存档。** 对象名里的哈希，就是 Software Heritage 给同一个目录的标识：`swh:1:dir:<hash>`。只有模式为 `100644` 的普通文件和模式为 `40000` 的目录的目录（对象正是这样，3.1），SWHID 规范 1.2 版第 5 条算出的值就是 2.2 的值。库公开并被存档以后，存档对这个目录的记录连同收录日期，就证明对象那时已经存在。作者可以请存档收录一个仓库。
  - **时间戳。** 时间戳目录里的证明（4.3）说明对象名在它给出的时间已经存在，可信的程度取决于做证明的服务。
  - **签名的提交**（6.3）说明是谁把对象放进了库，不说明什么时候。
  - 这些都不说明对象是谁做的，也不说明谁有权署名为作者。TOA 只提供证据：入口文件的 `author`（3.2.1）、来历（3.4）、签名和日期。由人来掂量；本标准对此不作判定。
- **SHA-1：** 对象的作者付出相当的代价，可以造出两个同名而内容不同的对象。经 git 传输时会被检测出来。索引还必须给每个对象记下对照值（2.2），同一个名字在不同位置对照值不同时报警。
- **私有库和公开库混用时，会带出去的东西：**
  - `history.json` 会带出全部内部祖先的名字。它在对象里，去不掉。
  - 来源表会带出地址；`ssh` 地址里的用户名可能是个人账号名。
  - 来源表里的 `label`、`refs`、`license` 是缓存的内容。所以没有公开来源的对象，发布时只留名字（5.3）。
  - 公开一个内部对象之前，工具必须按 5.3 列出这些。
- **符号链接：** 库里任何地方都不许有（6.1）。检出一个没查过的库之前，先看它的目录列表（7.3）。
- **解析：** 读任何文件、任何目录列表都有大小和深度的上限，并且先看大小再读。一个对象、一个旁挂文件、一个库出错，只影响它自己。
- **传给 git 的每个参数**（地址、提交号、分支名、路径）都不得能被读成选项：先按本标准的语法校验，再放到 `--` 之后，或确认不以连字符开头。

## 附录 B（说明性）留给以后版本的

`0.1` 版没有规定下面这些。在以后的版本规定之前，由部署和工具自己定，它们定的不算 TOA 的一部分。
